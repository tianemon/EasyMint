## 4. 委派机制核心改造（进行中）

**背景**:Mint 现在几乎全委派执行,不够灵活。委派机制设计初衷是**上下文保护**——新项目/大量新需求时,委派执行大量消耗 token 和占用上下文的任务(如读大量内容后总结),防止主会话被撑满、失去对项目的整体掌控;不是为了用 subagent 而用,要分场景。

**核心改造**(本次实施):
- 决策树从「任务复杂度」维度改为「**上下文保护 + 综合掌控**」双维度:
  - 第一优先(必须委派):大量内容读取/探索、产生海量中间输出的任务 → 委派白板子 agent,回传摘要
  - 第二优先(必须亲自):综合/决策/需求理解(cc: Never delegate understanding)、对用户反馈的直接响应
  - 第三优先(按上下文重合度):强依赖父会话当前上下文 → 亲自;独立可并行/需多样性 → 委派;简单任务(改几行/查报错/单文件)→ 亲自
- 硬约束:委派深度 = 1(子 agent 不得再委派,抄 Proma);委派类型化(探索型/审查型/实现型)

**涉及文件**:`app/shared/prompts.ts`(决策树 149-203 行)

**状态**:待实施(方案设计完成,落盘 `docs/design/Mint委派机制优化方案.md`)

## 5. 委派机制可选优化点（后续研究,暂缓）

调研 cc/Proma/dsh 三项目的委派设计后,以下机制可选装,先记录后续研究:

1. **cc 的 fork 判据**:委派前判断「这个中间输出我还用不用得到」——用不到/只想要结论才委派,需要逐行跟进则亲自
2. **cc 的 whenNotToUse 段**:tool description 里显式列「何时不用此工具」(如读文件/搜类别用 Glob/Grep/Read 自己查),给模型更明确的委派边界
3. **cc 的 continue vs spawn 决策表**:按「新任务与父上下文重合度」决定续派(继承)还是新派(零上下文)
4. **dsh 的 spawn/fork 双模式**:spawn=不继承上下文(offload 独立工作),fork=继承上下文(续接分析/审查);EM 可参考做「委派是否带上下文」
5. **dsh 的 maxDepth 可配置**:0=全禁委派,控制委派深度上限
6. **dsh 的后台默认**:独立委派同消息并行、主 agent 同时继续干活,仅当下一步依赖结果时才前台等待
7. **Proma 的委派类型化原语**:对抗式审查/多样性探索等具名委派类型,而非笼统「派个 agent」
8. **主会话模板能力附加(角色切换)**:模板=Mint 基础+能力段(如 Mint-D 设计能力),会话统一无 isDesigner,切换遵循「空白会话可切/聊过锁定」——与委派改造关联,见 `docs/design/Mint委派机制优化方案.md`

**状态**:暂缓(记录待后续研究)
