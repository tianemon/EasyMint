## 2026-06-17 更新

### 🐛 Bug 修复 — 新建项目后跳转聊天页空白

**根因**：`handleCreate` 中 `ask(initPrompt)` 是 fire-and-forget，固定等待 2 秒后跳转。SDK 落盘时间不确定——2 秒内未落盘时 `conv.messages` 读不到 `[系统消息] 项目已创建完毕`，ChatPanel 显示空白。重开页面重新调 `conv.messages` 才能读到。

**调试历程（6/16 晚 ~ 6/17 凌晨）**：

| 提交 | 尝试 | 结果 |
|------|------|------|
| `9a1164f` | init 消息预写入改为简短占位符 | 大文本卡渲染，不解决问题 |
| `ed16040` | 回退为固定等待 2 秒 | 有时 SDC 落盘超过 2 秒，不可靠 |
| `5286ba5` | `ask()` 发出后轮询 `conv.messages` 检查 `"[系统消息] 项目已创建完毕"` 是否落盘，每 100ms 一次，确认后立即跳转 | ✅ 可靠 |

**最终方案**：保留原有 `ask()` 流程不变，仅将固定等待改为轮询 SDK 落盘。ChatPanel、ProjectPage、chat-store 均未改动。改动仅 `NewProjectDialog.tsx` 一个文件 15 行。

## 1. 愿景

EasyMint 不再只是模板项目的 GUI 外壳，而是一个完整的 AI 开发平台。用户打开 App → 对话式创建项目 → 自动化开发 → 评估报告 → 持续性迭代，整个过程在一个持久会话中完成。

模板（ai-coding-automation-template）从"用户可见的产物"变为"EasyMint 内部的工作协议"——用户不知道也不关心模板存在，他只跟 AI 对话。

### 用户视角的完整流程

```
打开 EasyMint
  → Onboarding（检测 Claude Code，仅首次）
  → 进入工作台

  → 新建项目 / 打开已有项目

  → 【Chat 面板】与 AI 对话：
     "我想做一个 iOS 和 Android 都能用的记账 App"

  → AI 分析需求，逐步引导：
     问关键问题 → 内部调用对应表单 → 表单数据回传 AI → 继续对话

  → 需求确认完毕，AI 生成 requirements.md
     （内部执行：脚手架搭建 → task.json 生成 → init.sh 填充）

  → 用户点击「启动开发」
     → spawn 子会话循环跑 task.json
     → 每轮 builder + evaluator → 报告实时展示在 StreamPanel

  → 项目"完成"只是阶段性的：
     → 用户继续在 Chat 面板提新需求
     → AI 追加/修改 task.json
     → 启动新一轮自动化开发

  → 任何时候，新建 Chat 会话
     → AI 自动加载项目上下文（技术栈、已完成任务、会话摘要）
     → 像一位一直跟着项目的工程师一样接上
```

## 2. 持久会话架构

### 2.1 核心理念

**每个项目一个持久 Claude 会话。** 从项目创建到功能迭代，始终在同一条 `--resume` 链上。

### 2.2 会话模型

```
项目 A
  Chat 主会话（长会话，--input-format stream-json --output-format stream-json）
    ├── 需求访谈
    ├── 技术选型
    ├── 表单填写
    ├── 启动开发（spawn 子 worker）
    ├── 查看报告
    ├── 新需求讨论
    ├── 再次启动开发
    └── ...永久保持

  Worker 子会话（短会话，-p "按 WORKER.md 完成一个任务"）
    ├── Worker Round 1 → 提交 → 退出
    ├── Worker Round 2 → 提交 → 退出
    └── ...每轮独立，上下文来自文件（CLAUDE.md + task.json + progress.txt）

  Evaluator 子会话（短会话，-p "按 EVALUATOR.md 评估一个任务"）
    └── 每轮 Worker 后可选触发
```

### 2.3 会话生命周期

| 阶段 | 会话 | 说明 |
|------|------|------|
| 项目创建 | spawn 长会话 | `claude --input-format stream-json --output-format stream-json` |
| 需求采集 | 同上 | Chat 面板 = 这个会话的 stdin/stdout |
| 自动化开发 | 同上会话发起 | AI 内部调 `claude -p ...` 异步执行，不阻塞 Chat |
| 暂停/关闭 App | save session | session_id 持久化到项目元数据 |
| 恢复 | `claude --resume <session_id>` | EasyMint 启动时自动 resume |
| 新需求/修改 | 同上 | 用户随时在 Chat 打字，AI 追加 task.json，启动开发 |
| 新建会话讨论 | 可选 | 比如"帮我分析一下性能问题"，同样自动注入项目上下文 |

### 2.4 上下文管理

每个项目维护一个上下文快照文件 `~/.easymint/<project-id>/context.json`：

```json
{
  "project_id": "uuid",
  "claude_session_id": "sess-abc123",
  "created_at": "2026-05-28T10:00:00Z",
  "last_active_at": "2026-05-28T14:30:00Z",
  "profile": {
    "name": "个人记账 App",
    "type": "mobile",
    "platform": ["ios", "android"],
    "tech_stack": {
      "framework": "react-native",
      "styling": "tailwind",
      "backend": "firebase"
    },
    "requirements_summary": "iOS+Android 记账应用，支持分类统计、预算提醒、云同步、多设备",
    "completed_tasks": 15,
    "total_tasks": 18
  },
  "recent_conversations": [
    {
      "id": "conv-3",
      "title": "添加预算提醒功能",
      "summary": "用户要求添加月度预算设置和超支提醒，新增 3 个 task",
      "created_at": "2026-05-28T14:00:00Z"
    }

  "active_file_list": [
    "src/components/BudgetChart.tsx",
    "src/screens/AddTransaction.tsx"
  ]

```

**注入时机**：

- 新 Chat 会话创建时 → context.json 作为 system prompt 注入
- Worker 子会话启动时 → 不需要注入（它读 CLAUDE.md + WORKER.md + task.json）
- 项目恢复时 → `claude --resume` 自动恢复完整上下文

**更新时机**：

- 需求采集完成 → 更新 profile
- 任务完成 → 更新 completed_tasks，摘录 progress.txt 关键行
- 新对话结束 → 追加 recent_conversations，AI 自动生成摘要
- 文件变更 → 更新 active_file_list

## 3. 对话驱动表单系统

### 3.1 核心思路

**Chat 是主线，表单是辅助。** AI 通过对话理解用户意图，根据对话进程按需调用对应的结构化表单卡片。用户可以在卡片上直接操作，也可以继续打字让 AI 代填。

不是"用户填完表单 → AI 看结果"，而是"AI 和用户一起填"。

### 3.2 表单流转示例

```

  ┌─────────────────────────────┐
  │ 📋 项目概述                  │
  │ 名称: [记账 App_____]        │
  │ 平台: ☑ iOS  ☑ Android     │
  │ 类型: 移动端 App             │
  │ 描述: [___________________] │
  └─────────────────────────────┘

用户修改名称 → 填描述 → 点确认
  → 表单数据 JSONL → AI

AI 消息："明白了。移动端我建议用 React Native 同时覆盖两端，Firebase 做后
  端可以省掉服务器成本。你怎么看？" + 附带技术选型卡片

  ┌─────────────────────────────┐
  │ 🔧 技术选型                  │
  │                              │
  │ 前端框架:                     │
```

### 3.3 表单模板库

预置一组可组合的 form schema，每个 schema 是声明式 JSON，定义字段、校验规则、AI 推荐逻辑。不是写死的表单代码。

```
form-templates/
├── overview           # 项目概述：名称、平台选择、类型、描述
├── tech-frontend      # 前端框架选择（按项目类型提供不同选项）

│   ├── mobile         # React Native / Flutter / Swift+Kotlin / Expo
│   ├── desktop        # Electron / Tauri / WPF / SwiftUI

├── tech-backend       # 后端方案：Firebase / Supabase / 自建API / 无后端

├── database           # 数据库：PostgreSQL / MySQL / SQLite / MongoDB / 无
├── auth               # 认证：Firebase Auth / NextAuth / 自建 / 不需要
├── features           # 功能清单 P0/P1/P2（AI 根据项目类型预推荐）
├── ui-style           # UI 风格：色彩倾向、排版、组件库偏好
├── deploy-web         # Web 部署：Vercel / Netlify / Cloudflare / 自有服务器

├── deploy-desktop     # 桌面端分发：安装包 / 应用商店 / 压缩包
```

### 3.4 Form Schema 设计

每个 schema 包含：

```json

  "title": "选择前端框架",
  "description": "用于构建 iOS 和 Android 应用",

      "key": "framework",
      "label": "前端框架",
      "type": "radio",
      "ai_recommend": "react-native",
      "options": [
        {
          "value": "react-native",
```

AI 根据对话进程决定：

### 3.5 自适应规则

| 项目类型 | 需要的表单 | 跳过的表单 |
|---------|-----------|-----------|
| Web 前端 | overview + tech-frontend(web) + tech-backend + tech-styling + features + ui-style + deploy-web + budget + confirmation | deploy-mobile, deploy-desktop |
| 移动端 App | overview + tech-frontend(mobile) + tech-backend + tech-styling + features + ui-style + deploy-mobile + budget + confirmation | deploy-web, deploy-desktop |
| CLI / API | overview + tech-frontend(cli) + tech-backend + database + features + budget + confirmation | ui-style, deploy-*, tech-styling |
| 桌面应用 | overview + tech-frontend(desktop) + tech-backend + tech-styling + features + ui-style + deploy-desktop + budget + confirmation | deploy-mobile, deploy-web |
| 全栈（Web + 后端） | 全部，但如果 AI 推荐同一供应商则合并提示 | — |

### 3.6 用户自由对话的容错

用户不一定要在卡片上操作。如果用户放弃表单、直接打字：

```

AI：
- budget → "完全免费"
- framework → 按类型推荐免费方案
- backend → 选免费额度最高的
- 在 confirmation 卡片上展示全 AI 选择，用户确认即可
```

### 3.7 Chat 消息渲染 — 参考 open-design

Chat 面板的消息渲染采用 open-design 的分层展示模式：

**外层：最终对话流**
用户看到的是一条干净的双向对话。AI 的每条最终回复（text/markdown）直接展示，与用户消息交替排列，像聊天一样自然。

**内层：折叠的过程细节**
每条 AI 消息背后可能包含多个步骤，每个步骤默认折叠，点击标题展开：

- **思考过程** — AI 的 reasoning/thinking 内容，折叠为一行灰色小字 "🤔 思考中..."
- **工具调用** — Read/Write/Edit/Bash 等操作，折叠为 "🔧 Read file_path=xxx" 或 "📝 Edit app/xxx.tsx"
- **文件变更** — diff 摘要，折叠为 "📄 修改了 3 个文件"
- **子任务启动** — 启动 Worker/Evaluator，折叠为 "🚀 启动开发 — Task #5"

展开后可以看到完整的思考文本、工具参数/结果、diff 详情。

**视觉层次**：
```
🤖 AI: 好的，我来帮你实现这个功能。

  [展开] 🤔 思考过程
        分析了需求，这需要一个表单组件，先看看现有代码结构...

  [展开] 🔧 Read — app/src/App.tsx
         读取主入口文件，确认路由结构...

  [展开] 📝 Edit — app/src/components/NewForm.tsx
         创建新组件，包含表单逻辑...

  AI 最终回复: 已完成。新建了 NewForm 组件，路由已接入，你可以在 /new 看到。

👤 用户: 能加上表单验证吗？

🤖 AI: 当然可以。

  [展开] 🤔 思考过程
        需要添加验证逻辑...

  [展开] 📝 Edit — app/src/components/NewForm.tsx
         添加 required + pattern 验证...

  AI 最终回复: 已添加验证，包括必填字段和邮箱格式校验。
```

**关键设计决策**：
- 主对话流始终可见，不被过程细节打断
- 过程默认折叠，用户想看细节才点开
- 思考/操作/编辑三个层级用不同颜色/图标区分
- 过程步骤按时间顺序排列，不交错

## 4. 自动化开发流水线

### 4.1 流程

SETUP Phase 4-5 的逻辑内化为 EasyMint 的调度器，模板的 `run-automation.sh` 不再由用户执行，而是由 EasyMint 内部调度：

```
用户点击「启动开发」

  → spawn claude -p "按 WORKER.md 完成一个任务" --output-format stream-json

  → 任务完成（passes → true）
  → 如果评估模式开启 → spawn evaluator
  → 下一轮...
  → 直到全部 passes: true
```

### 4.2 进度可视化

- **StreamPanel**：实时展示 builder/evaluator 的 JSONL 流（文本、工具调用、文件变更）
- **右面板任务列表**：任务状态（pending / running / done / failed），点击查看步骤详情
- **Chat 面板**：AI 在每轮完成后发消息总结："已完成 Task 3/5，开始 Task 4..."

### 4.3 持续性开发

项目"完成"（全部 passes: true）不是终点：

```
用户: "这个记账 App 能加上语音记账吗？"

  2. 生成新 task(s) — 追加到 task.json

  → 新一轮自动化开发（只做新追加的任务）
```

## 5. 实现计划

### 阶段 1 — UI 布局（当前）

纯 UI + Mock 数据，不接入 Claude。确认交互流畅、设计一致。

### 阶段 2 — 基础 Chat

实现真正的 Chat 面板 + 长会话 spawn。Mock 数据替换为实际 JSONL 流。

### 阶段 3 — 表单系统

表单模板库 + 对话内嵌卡片 + AI 路由逻辑。先做 Web 类型的表单链，再扩展移动端/CLI。

### 阶段 4 — 自动化流水线

agent-service 完整实现：worker 调度、evaluator 触发、progress 流转。同时把 `run-automation.sh` 和 `evaluate.sh` 用 Python 重写。

#### 为什么改用 Python

当前 bash 脚本的问题：

- **JSON 操作靠内联 python3 -c**，每次读 task.json 都要 spawn 一个 Python 子进程
- **轮询/超时/grace period 逻辑** 在 bash 里用 while + sleep + 时间戳比较，可读性和可维护性差
- **错误处理散落 `|| true`**，容易掩盖真实问题
- **跨平台**：bash 在 Windows 上需 WSL，Python 直接跑

#### 重写后结构

```
run_automation.py <runs> [--evaluate]   # 替代 run-automation.sh
evaluate.py [--task <id>]               # 替代 evaluate.sh
init.sh                                  # 保持不变，就几行环境检测
```

#### Python 脚本职责

`run_automation.py`：
- 读取 task.json → 选未完成任务
- spawn claude 子进程（带 sandbox 包裹）
- 轮询检查 task.json passes 字段
- 检测到 passes:true → 等待 Claude 自然退出（grace period）
- --evaluate 模式下每轮后触发 evaluator
- 日志写结构化 JSON，进度同步到 progress.json

`evaluate.py`：
- 读取 task.json → 选待评估任务
- spawn claude 子进程（按 EVALUATOR.md 评估）
- 等待完成后读取报告文件
- 更新 task.json evaluated 字段

#### 关键接口

```python
# 读取任务状态 — 不再 python3 -c 内联
with open("task.json") as f:
    tasks = json.load(f)["tasks"]

# 轮询 — Python 原生控制流
task_done_at = None
while True:
    time.sleep(60)
    if check_task_done(task_id):
        task_done_at = time.time()
        # 等 Claude 自然退出...
    if task_done_at and (time.time() - task_done_at) > 120:
        process.kill()  # 超时强制终止

# 错误处理 — 明确的 try/except
try:
    process = subprocess.Popen(...)
except FileNotFoundError:
    log.error("Claude CLI 未找到")
```

#### 保留的文件

- `init.sh` — 保持 bash，功能简单且需要用户终端直接执行
- `run-automation.sh` / `evaluate.sh` — 可保留为对 Python 的轻量 wrapper（兼容原有习惯）
- 跨平台（Windows 也能跑），`init.sh` 保持 bash

### 阶段 5 — 上下文管理

context.json 维护、会话 resume、新会话自动注入。

### 阶段 6 — 持续性开发

task.json 动态追加、增量开发、历史会话管理。

### 阶段 7 — CLI → SDK 迁移

当前 `agent-service.ts` 通过 `child_process.spawn("claude")` 运行 Worker/Evaluator。迁移至 `@anthropic-ai/claude-agent-sdk` 的 `sdk.query()`。

#### 动机

| | CLI spawn（现状） | SDK `query()` |
|---|---|---|
| 进程管理 | 手动 spawn/kill/wait/grace period | SDK 内部管理 |
| 输出格式 | 解析 JSONL 字符串 | 类型安全 `SDKMessage` |
| 权限控制 | `bypassPermissions` 一刀切 | `allowedTools` 白名单 + `canUseTool` 逐项决策 + `hooks` 拦截 |
| 沙箱 | 外部 `sandbox-exec` 包裹 | 内建 `sandbox` 配置 |
| 会话 resume | 手动拼命令 | `query({ resume: sessionId })` |
| 生命周期 | 进程级 | Hook 回调（PreToolUse/PostToolUse/Stop/SessionEnd） |
| 依赖 | 用户安装 `claude` CLI | npm 包，零用户配置 |
| 审计 | 自己写 | Hook 天然支持 |
| 费用 | 消耗 Pro/Max 订阅额度 | 配 DeepSeek API Key 走 DeepSeek 账单，无 Anthropic 费用 |

#### 改动范围

```
agent-service.ts      → 删掉 spawn/JSONL 解析，改为 sdk.query() for-await 循环
jsonl-parser.ts       → 可移除（SDK 已返回结构化消息）
run-automation.sh/py  → 简化，不再管进程超时/kill/grace period
claude-detector.ts    → 改为检测模块：SDK 可用 + 可选 CLI fallback
```

#### 兼容性

- DeepSeek 通过 `ANTHROPIC_BASE_URL` + `ANTHROPIC_API_KEY` 环境变量接入，SDK 和 CLI 走同一套底层
- 安装为 npm 依赖，无需用户手动装 CLI
- 权限细粒度：允许 Read/Write/Edit，禁止 Bash `rm -rf`/`sudo`/`curl | bash`，Hook 实时拦截

### 阶段 8 — EM + OD 协作

EasyMint 接入 open-design，需求确认后、开发开始前，可选生成 UI 原型。原型确认后再启动自动化开发，确保首轮结果符合用户预期。

| 项目类型 | EM 默认行为 |

## 7. 流程控制与稳定性

### 7.1 行为监控

所有 Worker 和 Evaluator 的运行状态必须实时可观测：

- **Worker 监控**：当前任务 ID、开始时间、已耗时、JSONL 事件计数、最后事件类型
- **Evaluator 监控**：当前评估的任务、截图数、image-vision 调用数、当前状态
- **进程健康**：子进程 PID、CPU/内存占用、是否僵死
- **监控面板**：StreamPanel 上方或侧边显示简版状态栏，异常时变色
- **事件日志**：所有 spawn/exit/error/kill 事件记入结构化日志

### 7.2 开发锁 + 需求队列

开发进行中锁定项目，新需求排队，本轮完成后统一处理：

```
用户提需求
  → 如果开发进行中：
    → 需求进入队列（显示 "需求已加入队列 #3"）
    → 队列 UI：右侧面板或 Chat 侧边，可拖拽排序
  → 如果开发未运行：
    → 直接追加 task.json → 启动新一轮

本轮开发完成
  → 自动 flush 队列：
    → 按优先级顺序将积攒需求合并到 task.json
    → 启动新一轮开发
    → 队列清空
```

## 8. 沙箱隔离

### 8.1 问题

Worker 和 Evaluator 需要 `--permission-mode bypassPermissions` 才能自动化运行，但 bypass 之后 CLI 内建的权限弹窗不会触发，CLAUDE.md 的安全约束本质上靠 prompt 遵守，没有物理兜底。

### 8.2 方案

**macOS：sandbox-exec + 动态 .sb 配置**

```bash
# EasyMint 在 spawn 前根据 project.path 动态生成 sandbox 配置
cat > /tmp/easymint-worker-${runId}.sb <<EOF
(version 1)
(deny default)
(allow file-read* file-write* (subpath "${project.path}"))
(allow file-read* (subpath "/opt/homebrew"))
(allow file-read* (subpath "/usr/local"))
(allow file-read* (subpath "/private/var/db/xcode_select_link"))
(allow process*)
(allow sysctl*)
(allow network* (local ip))
EOF

sandbox-exec -f /tmp/easymint-worker-${runId}.sb \
  claude -p "..." --permission-mode bypassPermissions
```

**Windows：AppContainer + Low Integrity Level**

```powershell
# 首次创建隔离容器
New-AppContainerProfile -Name "EasyMintWorker" -DisplayName "EasyMint Worker" ...

# spawn 时限定
Start-Process -AppContainer "EasyMintWorker" -Wait -NoNewWindow claude ...
```

### 8.3 能力白名单

| 操作 | 是否允许 | 原因 |
|------|---------|------|
| 读写目标项目目录 | ✅ | worker 只需操作当前项目 |
| 读 node/npm/claude 工具链 | ✅ | 开发工具链路径 |
| npm install（外网） | ✅ | 依赖下载 |
| Vite dev server localhost | ✅ | 开发预览 |
| curl API 测试 | ✅ | 后端验证 |
| git commit | ✅ | 在项目目录内的 .git 操作 |
| 读 ~/.ssh 私钥 | ❌ | 禁止访问用户凭证 |
| 读 ~/Documents、~/Desktop | ❌ | 禁止访问用户数据 |
| 写 /etc、/System | ❌ | 禁止修改系统 |
| 读写其他项目目录 | ❌ | 项目间物理隔离 |
| 外网 curl（非必要） | ❌ | 默认禁止，按需放开 |

### 8.4 关键设计决策

- **项目不动**：沙箱管进程，不管文件。项目仍在用户选的目录，Worker 被物理锁在该目录内
- **动态配置**：每个 Worker/Evaluator spawn 时根据 project.path 动态生成临时沙箱配置
- **平台适配**：macOS sandbox-exec（内建），Windows AppContainer（内建），跨平台无需额外依赖
- **最坏情况**：bypassPermissions 模式下 Claude 即便完全失控，也只能毁掉当前项目，碰不到用户的其他数据

## 10. Task 系统重构（2026-08-02）

### 10.1 背景与问题

- **同步阻塞**：task 工具的 execute `await runSubagents` 等全部子 Agent 完成才返回 → Pi 模型循环卡在 `await executeToolCalls` → Mint 全程停摆,用户插话(steer)排队等待
- **收集 bug**：executor 对 `message_update`(每帧累积全文)逐帧 push → 逐词递增重复文本;agent_end 竞态导致偶发空结果
- **平级会话**：子 Agent 会话落盘 `~/.easymint/sessions/<项目>/` 与主会话平级,出现在会话列表
- **无结构化输出**：outputSchema 传了但 yield 未实现("not ported yet")
- **不可中断**：无 abort 机制

### 10.2 架构(对齐 cc 异步委派实测行为)

```
task 工具 execute → registry.createDelegation(立即返回"已启动 N 个子 Agent")
  → executor.runSubagents 后台执行(不 await)
  → 完成 → registry.finishDelegation → completion resolve
  → agent-service.injectSystemMessage([系统消息]-[Agent执行结果] 注入主会话)
  → Pi 自动开新回合 → Mint 汇报
用户点打断 → abort 只停主会话回合(子 Agent 不受影响,对齐 cc 实测)
子 Agent 单独停止 → AgentBar 任务列表 → abortTask(每任务独立 AbortController)
```

### 10.3 模块

| 模块 | 职责 |
|------|------|
| `task/registry.ts`(新) | 委派记录表:delegationId/parentSessionId/status/completion/abort + taskAbortControllers(单任务停止)+ 临时 ID→真实 ID 映射 |
| `task/collector.ts`(新) | 结果收集:按消息 id 替换(治重复/空)+ yield 结构化组装 |
| `task/yield-assembly.ts`(移植) | omp yield 组装逻辑(去 @oh-my-pi 依赖,arrayValuedLabels 轻量等价) |
| `task/executor.ts`(重构) | 后台执行、subagents/ 子目录落盘、任务级中断传播、collector 接入 |
| `task/tool.ts`(重构) | execute 异步委派:立即返回「已启动」,completion 回调经 onComplete 注入主会话 |
| `pi-session.ts` | createPiSession 支持自定义 sessionDir(子 Agent 落 subagents/)+ registerSessionIdMapping |
| `agent-service.ts` | injectSystemMessage(系统消息注入)+ stopDelegationTask(单任务停止)+ pendingSystemMessages(忙碌时积压兜底) |

### 10.4 关键决策

- **异步委派 + 系统消息注入**(最终决策,cc JSONL 实测实证)：execute 立即返回"已启动 N 个子 Agent",不阻塞回合;完成 → `record.completion.then` → onComplete → injectSystemMessage 注入 `[系统消息]-[Agent执行结果]` 前缀系统消息 → Pi 自动开新回合,Mint 汇报。实证依据:cc 的 execute 返回 `{isAsync, status:"async_launched"}`,完成通知以 **user 角色 + origin:task-notification** 注入并自动触发新回合。此前"同步等待 + steer 注入"方案被实测否定:steer 是 user 角色,结果会以用户视角出现在对话
- **打断与子 Agent 解耦**：用户点打断(abort)只停主会话回合(executor signal 监听直接 session.abort),后台子 Agent 继续执行;子 Agent 经 AgentBar 任务列表**单个停止**(abortTask,每任务独立 AbortController)——对齐 cc 插话不杀子任务实测
- **注入消息渲染**：`[系统消息]` 前缀 = 系统事件,前端渲染绿色结果气泡(● 摘要行,红绿灯三色)/居中灰字胶囊;event-bridge 仅转发 `[系统消息]` 开头的 user 消息(防重复渲染)
- **收集哲学**：message_update 每帧累积快照 → 按消息 id 替换(与渲染层 replaceAiEntriesById 同一哲学)
- **分级落盘**：子 Agent 会话落 `<sessions>/<项目>/subagents/`(listPiSessions 不递归子目录→列表不可见)
- **信号栈状态栏**：pushSignal/popSignal 先来后到,「调用 Agent」常驻至委派结束
- **删除 vendor/omp/**(36 文件死代码):task 系统完整自研,不再复制 omp 源码

## 11. 后台 Shell 功能（2026-08-02）

> 对齐 Claude Code `run_in_background`:Mint 可发起不阻塞对话的长驻命令,
> 退出后结果自动注入主会话。

### 11.1 背景

Pi SDK 的 bash 工具无 background 参数(输入仅 command + timeout,同步阻塞)。
经源码实证:前台 bash 天生流式(`tool_execution_update` 带 partialResult 累积快照),
缺的只是「立即返回 + 后台执行」。

### 11.2 实现

| 层 | 文件 | 职责 |
|----|------|------|
| 工具层 | `background-shell/tool.ts`(新) | 增强 bash:前台委托 Pi 原生;`background: true` → spawn 立即返回 |
| 进程层 | `background-shell/registry.ts`(新) | 注册表:start/stop(杀进程树)/输出尾部截断 4KB/退出广播 |
| 通知层 | `agent-service.ts` | `onShellExit` → 临时 ID 解析 → `injectSystemMessage` 注入结果 |
| UI 层 | `ShellBar.tsx` + delegation-store | shell·N = 后台命令数,浮层列表 + 单条停止(与 AgentBar 同款) |

### 11.3 关键决策

- **前台委托原生**:同步执行 + 实时流式输出零改动;后台分支立即返回不阻塞
- **完成通知**:`[系统消息]-[Agent执行结果] ● 后台命令 — 完成/中止/失败 · Ns + 输出`,
  前端按红绿灯三色渲染(与委派通知同一渲染路径)
- **shell·N 语义变更**:由「所有工具执行计数」改为「后台命令数」,由 `agent:shell-count`
  广播驱动;前台瞬时工具不再计入(顺带废弃 tool_execution_update 多帧重复累加逻辑)
- **输出截断**:尾部 4KB,超长丢中间(防消息体膨胀)
- **清理**:应用退出(agentService.shutdown)stopAll 杀进程树,防孤儿进程

## 12. Custom 消息角色迁移（2026-08-02）

### 12.2 实现

| 层 | 改动 |
|----|------|
| prompts.ts | 新增 `systemMessage(kind, content, extra?)` 辅助:customType 统一 `system_message` + details.kind 细分 |

| rotation | handoff 迁移(kind: handoff);依赖注入补全 images/systemPayload 透传 |
| event-bridge | role custom + customType system_message → `custom_event`(透传 text/timestamp/details);删除旧前缀转发 |
| 前端 | ChatPanel 收 custom_event 入 store(带结构身份);MessageItem 按 details.kind 渲染(delegation/shell → 绿色气泡,其他 → 灰字胶囊) |
| session-service | getSessionMessages 扩展 custom_message 条目(轮询与重载的前提) |

### 12.3 关键决策

- **customType 统一 `system_message` + details.kind 细分**(对齐 cc `promptSource: "system"`);
  kind: delegation / shell / project-created / flow / handoff / summary
- **content 保留 `[系统消息]` 前缀**:convertToLlm 映射 custom → user,模型侧识别依赖内容;

- **不做旧数据兼容**(EM 未正式发布):旧 user 形态前缀消息直接废弃
