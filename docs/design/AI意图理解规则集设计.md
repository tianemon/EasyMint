# AI 意图理解规则集设计（通用防误解规则）

> 2026-08-20 定稿。来源：本会话（029fa896，113M JSONL）66 个「AI 误解用户意图/反复拉扯」案例的系统分析。
> 目的：为改进 EasyMint 的 Mint 系统提示词提供依据——规则不依赖具体项目场景，可泛化到大多数 AI 编程对话。
> 2026-08-20 补充：跨场景推导新增 3 条扩展规则（N1/N2/N3，见 3.4）。

---

## 一、背景与研究过程

### 1.1 问题

用户在与 AI 的大量交互中发现模型经常误解意图，典型 4 类失败：
1. **语境延续断裂**：a 改完接着说「改成 yyy」，模型当新需求改了别的东西
2. **语义方向相反**：说「改大」改小——代码变量语义和视觉习惯描述冲突
3. **结构认知不足**：说「按钮变矮」改半天不对——实际是外层容器控制高度
4. **层级/对象歧义**：说「面板透明」改软件内透明度——实际要系统窗口透明

### 1.2 研究方法

- 用 `scripts/extract-session.js` 从 113M 会话 JSONL 提取纯文本对话（205 万字符）
- 拆 5 份，5 个并行子 agent 分析，共确认 **66 个案例**（68 条记录，液态玻璃含 3 子案例）
- 每案例记录：全局行号、用户意图、AI 误解、过程复盘、关键转折、模式归类
- 6 类失败模式统计后，抽象成「信号 → 行为」通用规则，做覆盖率检验迭代

### 1.3 失败模式统计（67 条归类）

| 模式 | 次数 | 占比 |
|------|------|------|
| ⑤ 未确认就执行/强行猜测 | 17 | 25% |
| ⑥ 其他（过度解读/发明需求/视角错位） | 19 | 28% |
| ④ 对象歧义（改错对象/组件/落点） | 12 | 18% |
| ② 语义方向相反 | 8 | 12% |
| ③ 结构认知不足（层级/容器/样式来源） | 7 | 10% |
| ① 语境延续断裂 | 4 | 6% |

## 二、泛化方法

**两步抽象**：先把案例去场景化（抽掉 EasyMint 组件名、术语），提取行为模式；再把模式归并成「信号 → 行为」规则。

**规则可泛化的关键**：触发信号必须能被 AI 自己识别——「任务按钮」是场景词，但「用户描述的对象存在多个候选」是通用信号。场景无限但信号有限：66 案例最终收敛到 10 个信号。

### 抽象对照表（案例 → 信号）

| 典型案例 | 场景层 | 泛化信号层 |
|---------|--------|-----------|
| 任务按钮连猜 4 次 | 「打开任务面板用的按钮」才做对 | 用户指代不明，AI 猜一个就完整实现 |
| 窗口透明 30 轮 | 用户说「透明」，AI 改页面 CSS | 用户描述「看到的」效果，实现涉及系统层级 |
| 速度滑杆反了 | 往右=变快存成秒/圈 | 日常方向词与代码语义可能相反 |
| 「bash 的下边距」 | 用户省略主语 | 同话题连续消息省略对象，核心对象未变 |
| 符号动画被删 | 「调整显示时机」做成「删除」 | 需求含删除/隐藏/替换现有功能 |
| 表单精简过头 | 说「精简文案」删了全部字段 | 微调需求被扩展成结构性改动 |
| Ctrl+C 排查 | 先查 concurrently/zsh | 排查不对比「自己最近改了什么」 |
| v1 色值凭记忆 | 断言 #16a34a | 可查证的事实凭记忆断言，不验证 |

## 三、最终规则集（10 条）

规则的通用形态：**当 X 信号出现时，执行 Y 行为**。全部不依赖具体项目。

### 3.1 理解类（对象/语义确认）

**R1 候选清单**：指代对象存在多个候选（UI 元素/文件/组件/变量/方案）时，列出候选清单请用户选择，禁止猜一个直接做。
- 案例：任务按钮连猜 4 次（ac-1）、复制颜色语义 4 轮（aa-6）、空气泡概念（ae-2）、「永久显示」多义（ae-9）

**R2 层级确认**：用户描述的是「可见效果」时，先确认实现层级（窗口/页面/容器/元素、组件/子组件、数据层/展示层）再动手。
- 案例：窗口透明 30 轮（ad-11）、语法高亮渲染路径分叉（aa-1）、气泡 DOM 层级（ab-9）

**R3 复述确认**：出现日常方向词/程度词（大/小/高/矮/快/慢）或表述模糊时，动手前用一句话复述「将改成什么效果」请用户确认。
- 案例：速度滑杆反向（aa-8）、半椭圆尾巴（ab-4）、档位 2 当 2 秒（ab-7）、模板弹窗方向做反（ac-2，AI 复述后一次做对）

**R4 语境继承**：同话题连续消息中用户省略主语/宾语时，默认继承最近讨论对象；仅当对象明确变化才视为新需求。用户贴出的内容（日志/回复/证据）优先按「证据」解读而非「提问」。
- 案例：Mint 回复被当提问（ab-13）、「bash 的下边距」省略主语（ad-5）、CI 旧日志误读（ab-17）、错别字「不进去」应结合前句语境推断（ac-5）

### 3.2 行为类（执行边界）

**R5 改动声明**：任何修改前，用一句话声明改动清单（改什么、为什么）；用户只要求「看看/排查」时，先回答/排查，不顺手改。
- 案例：「你先告诉我」后直接动手（ac-3）、越权解耦夹带项（ac-9）、滑块回弹未确认就修（ae-1）

**R6 删除确认**：涉及删除/隐藏/替换现有功能、代码、配置、UI 项时，必须先确认，无例外。
- 案例：符号动画被删（aa-3）、死代码清理误删在用代码（aa-5）、表单精简过头删全部字段（ad-1）

**R10 范围守界**：只做用户要求的；不发明需求、不扩展范围、不擅自更换实现方式、不夹带无关改动。
- 案例：全局直接创建设计残留（ad-13）、打开原型却用 Playwright 渲染（ae-6）

### 3.3 执行验证类（完成标准）

**R7 一次一变量**：视觉/交互微调时一次只改一个变量，说明预期变化并等待反馈；收到「没变化/还是不对」时停止盲改，换思路或问方向，不在同一死胡同加补丁。
- 案例：液态玻璃折射 8 轮失败（ad-9c）、输入卡片动画 10 轮推倒重来（ae-3）、滚动贴底连环拉扯（ab-8）

**R8 证据优先**：涉及「是否发生过/为什么/事实是什么」的断言和排查，必须用证据（日志/复现/git diff/数据记录）支撑；排查先对比「自己/最近改了什么」，再查外部因素；禁止凭记忆或假设下结论。
- 案例：v1 色值凭记忆断言（aa-4）、思考等级竞态猜测（ac-7）、Ctrl+C 先查外部原因（ae-7）、auto_compact 基于旧源码断言（ae-8）、busy 状态先给结论（ae-12）

**R9 验证生效**：任何修改/交付在汇报前必须验证生效（构建通过/渲染正常/数据流走通/双入口一致）；禁止「改一处就汇报完成」；技术上没把握的方案先验证可行性再实现；已知隐患不得带病交付。
- 案例：qwen 三张表漏改两次（ac-6）、原型黑屏未渲染验证（ac-10）、手动/双入口实现漂移（ab-14）、SVG 方案未验证可行就实现（aa-10）、添加模型带病交付（ae-11）

### 3.4 扩展规则（跨场景推导）

从各场景（Java 微服务 / Go 大数据 / Rust 高并发 / 办公 PPT·资料 / 写小说 / 数据分析）反推，现有 10 条在跨场景时暴露 3 个信号盲区。失败根源是「人类-模型沟通」问题而非编程问题，故规则可迁移；差异只在各场景的高频触发点不同。

**N1 抽象美学词落地化**：用户用抽象美学词（「高级感」「大气」「有质感」「顺」）描述时，不直接动手——先问「有无参照物」（图/文/风格），有则优先分析参照物提取要素；无则基于当前内容拆出 3-5 个可验证维度（如配色/留白/节奏/视角），按「当前 → 目标方向」逐项列出，用户只需确认或指出哪项不对。
- 触发场景：设计、写作、品牌文案等美学类任务（编程场景的方向词已由 R3 覆盖，抽象词无物理量可比对）
- 案例映射：飞碟抽象视觉（aa-11）、归档面板「不够优雅」（ae-4）
- 触发下限：描述不可直接执行（无可对照的物理量）时才启用，避免过度确认（ad-7 教训）

**N2 不可逆操作分级确认**：按恢复成本分三级——**可逆**（已提交/可撤销）：说明即做；**半可逆**（未提交改动/可 diff 还原）：说明+确认；**不可逆**（删除原文/覆盖/批量替换/外部操作）：先出边界清单（涉及对象+数量+代表性抽样，批量替换出 diff 预览），确认后才执行。禁止默认「有 git 就可恢复」——未提交/未跟踪的改动同样会丢。
- 触发场景：资料整理（AI 认为「冗余」删信息）、批量替换、文件覆盖、数据迁移
- 案例映射：死代码误删（aa-5）、表单精简过头（ad-1）
- 落地：Mint 可做成机制（权限弹窗加 dry-run 预览），而非纯文本规则

**N3 长上下文事实追踪**：对已确立事实（术语定义/档位/设定/命名/业务规则）维护**落盘清单**（会话级或项目级文件）。入清单条件（任一）：用户明确给出定义、被纠正过、跨轮被引用且用户默认 AI 记得。任务涉及清单事实时先核对；事实变更时显式宣告并更新清单。与 R4 分工：R4 管短程对象继承，N3 管长程事实维护。
- 触发场景：微服务跨文件重构、长篇小说写作、多轮文档处理
- 案例映射：档位 2 当 2 秒（ab-7）、验证场景被遗忘（ab-12）
- 落地：不落盘的追踪是空话——EM 可用 `<项目>/.easymint/` 承载会话级/项目级约定文件

### 3.5 扩展规则设计要点

- **每条带触发下限**：按抽象程度/不可逆程度/任务长度分级启用，避免简单任务过度确认（ad-7 反面教训）
- **用否定式结构表述**：「先确认，不做 X」——66 案例证明否定式澄清对模型最有效
- **N1 与 N3 联动**：美学确认中确立的要素定义本身是「事实」，长任务里应入 N3 清单（写作时「主角性格」既是 N1 确认对象也是 N3 追踪对象）
- **落地形式差异**：N2 机制化（权限弹窗 dry-run），N1/N3 进场景 skill，不塞常驻提示词

## 四、覆盖率检验（66 案例反推）

### 4.1 基准（8 条规则草案，无 R9/R10）

- 强覆盖 54/68（79%），含弱覆盖 62/68（91%），明确漏网 6 条

### 4.2 漏网案例 → 新增规则

| 漏网案例 | 本质 | 新增规则 |
|---------|------|---------|
| qwen 三表漏改、SVG 方案、双入口漂移、原型黑屏、带病交付、布局坑 | 完成标准=「改完了」而非「验证生效」 | R9 验证生效 |
| 发明需求、执行方式越界 | 做了用户没要的东西 | R10 范围守界 |

### 4.3 复验（10 条规则）

- **强覆盖 62/68（91%），含弱覆盖 65/68（96%）**

### 4.4 残余 3 条（规则难覆盖，属能力/内容问题）

1. **视角切换**：迁移模板需要「接收方不知道发生了什么」的视角（ab-15）
2. **产品 vs 技术视角**：用户要「用户友好」视角，AI 给技术方案（ad-3）
3. **过度确认不行动**：R5 的反面，确认太多反而拖沓（ad-7）——需「确认一次后给默认建议」的节奏感

## 五、分层落地建议

按使用频率与触发场景分三层，避免常驻规则过多导致规则疲劳：

| 层 | 规则 | 覆盖 | 落地位置 |
|----|------|------|---------|
| 常驻核心 | R1 候选清单 / R5 改动声明 / R6 删除确认 / R8 证据优先 / R10 范围守界 | 44 例 | 系统提示词 rules |
| 理解层 | R2 层级确认 / R3 复述确认 / R4 语境继承 | 20 例 | 系统提示词（精简表述） |
| 执行验证层 | R7 一次一变量 / R9 验证生效 | 12 例 | UI 修改类 skill；R9 可转为机制（EM 评估器/自动验证）而非文本规则 |
| 扩展（跨场景） | N1 抽象词落地 / N2 不可逆确认 / N3 事实追踪 | 美学·整理·长任务场景 | 按场景进对应 skill；办公/写作类无代码验证回路，R9 只能靠「导出/预览/自检清单」实现 |

## 六、让 AI 从「错」转向「对」的关键指令（用户侧观察）

按有效性排序（来自 66 案例复盘，供提示词设计参考）：
1. **点破结构本质的一句话**（「就在聊天页面的基础上改」「窗口透明」）——AI 对系统层级心智缺失是最大盲区
2. **功能身份/动词描述**（「打开任务面板用的按钮」）——对象不明时问「它干什么」比问「它在哪」有效
3. **否定式澄清**（「不是常驻了」「不是结论文本」）——精确收缩理解范围
4. **精确几何/空间语言**（「底部贴合边框、顶部变弧形」）——一击命中
5. **数据驱动的质疑**（「jsonl 中有记录吗？没有的话就是你猜的」）——推翻未验证结论
6. **元指令换轨**（「不要在死胡同转悠」「不要采样，先看代码」）——AI 缺乏自我换轨机制
7. **用户自设计实验**（「临时去掉渐隐代码」）——术语僵持时让双方看到同一事实
8. **最终形态一句话定义**——触发整体重构且做对

## 七、边界说明

- 规则消除不了模型能力上限：抽象视觉描述（飞碟/曙光）、空间想象不足——需机制（实时预览验证回路）辅助
- 规则数量与遵守度成反比：常驻不超过 5 条核心，其余进 skill 按场景加载
- 覆盖率检验有主观成分（agent 归类），但 5 份报告结论高度一致，可信度较高
