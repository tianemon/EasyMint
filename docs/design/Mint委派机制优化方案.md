# Mint 委派机制优化方案

> 状态：已定稿待实施（2026-08-14）
> 背景：Mint 现在几乎全委派执行，不够灵活。本文设计以「上下文保护」为核心的委派决策树。

---

## 一、问题与初衷

**现状问题**：Mint 收到任务几乎全走委派 Builder，只有 ≤20 行小微修改才亲自做（`prompts.ts:149-203`）。这导致：
- 简单任务也付委派开销（建子会话、上下文交接、结果回传）
- Mint 亲自读大量文件占主上下文，该委派的读取反而亲自了

**设计初衷**（用户定义）：委派机制的核心价值是**上下文保护**——
- 新项目 / 大量新需求 / 新改动时，委派执行**大量消耗 token 和占用上下文**的任务（如读大量内容后总结），防止主会话被快速撑满、失去对项目的整体掌控
- 不是为了用 subagent 而用，而是分场景

## 二、参考项目调研结论

| 项目 | 委派哲学 | 可借鉴点 |
|------|---------|---------|
| **cc** | 主 agent 默认亲自干活，子 agent = 并行独立查询 + 保护上下文窗口 | ① fork 定性判据「中间输出还用不用得到」；② 强制「综合留父」Never delegate understanding；③ tool description 有 whenNotToUse 段 |
| **Proma** | 主 agent 亲自执行为默认，协作是 opt-in skill | ① 「不适合委派」清单（简单搜索/单文件读/强依赖父上下文）；② 子会话深度=1 不得再委派；③ 委派类型化（对抗式/多样性） |
| **dsh** | 无「小任务别委派」显式规则；子 agent 分 spawn（不继承）/ fork（继承） | spawn 措辞「offload work so it does not consume this conversation's context」——正是上下文保护初衷 |

## 三、核心设计：委派决策树（双维度）

按优先级判断：

### 第一优先：必须委派 —— 上下文保护
- 要读/探索大量内容（>N 文件、大量搜索、深调研）然后产出 → 委派白板子 agent，回传摘要
- 会产生海量中间输出的任务（长测试、大日志分析、批处理）
- **判据（cc 定性）**：「这些中间内容如果进主会话，我还用不用得到？」→ 用不到/只想要结论 → 委派；需要逐行跟进 → 亲自

### 第二优先：必须亲自 —— 综合与掌控
- 方案的最终综合、决策、需求理解（cc: Never delegate understanding）
- 项目整体走向的判断
- 对用户反馈的直接响应（对话本身）

### 第三优先：可选的亲自 vs 委派 —— 按上下文重合度
- 强依赖父会话当前上下文（接着刚才讨论做）→ 亲自（Proma：拆出去增加同步成本）
- 独立、可并行、需要多样性（多方案对比、对抗审查）→ 委派
- 简单任务（改几行代码、查个报错、单文件读）→ 亲自

### 硬约束
- **委派深度 = 1**：子 agent 不得再委派（抄 Proma，防止委派链失控）
- **委派类型化**：明确「探索型 / 审查型 / 实现型」，不是笼统「派个 agent」

## 四、落地改动

**涉及文件**：`app/shared/prompts.ts`（决策树 149-203 行）

**改动内容**：把「任务复杂度」维度改为「上下文保护 + 综合掌控」双维度决策树（见第三节），替换现有「小微修改自己做 / 其余委派 Builder」逻辑。

**保持不动**：Builder/Evaluator 模板、委派执行流程（task.json → Builder → Evaluator）、task.json 状态机。
