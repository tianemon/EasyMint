# 系统提示词模块化与场景装配设计

> **状态**：设计稿 2026-08-13。背景：MINT_SYSTEM_PROMPT 是 252 行静态字符串，规则全量常驻导致"规则淡化"（低频关键规则被注意力稀释）；用户希望学 Claude Code 做 section 化 + 按需拼接。
> **定位**：本文件定义 EM 系统提示词的模块化拆分、按场景装配、轮转重拼、常驻/skill 分层的完整方案，供实现参考。

---

## 〇、现状与问题

**现状**（已核实）：
- `MINT_SYSTEM_PROMPT`（prompts.ts:11-262）是一个静态大字符串，8 个 `<section>` 标签（identity/language/easymint/guide_user/system_message/ui_tools/creation_flow/rules）
- `buildSystemPrompt`（agent-service:508-528）一次性拼接：`MINT_SYSTEM_PROMPT`（resolveEffectivePrompt）+ skills 段 + env 段 + profile 段
- `prompt-sections.ts` 已有"稳定核心静态 + 动态段运行时构建"雏形（注释明写"借鉴 cc section 组装"），但只用于 env/profile 两个动态段
- **轮转时重拼**（rotation.ts:100 调 buildSystemPrompt）——天然是"重拼"入口

**问题**：
1. **规则淡化**：252 行全量常驻，注意力稀释；低频关键规则（渲染自查/Gate/成本引导）被淹
2. **场景错配**：创建引导规则与开发执行规则混在一串，引导期不需要开发详规、开发期不需要创建详规，但都常驻
3. **静态不可变**：Pi SDK 的 systemPrompt 创建时固定（`systemPromptOverride`），无 turn 级更新 API

**硬约束**（决定方案上限）：
- Pi `createAgentSession` 的 systemPrompt 创建时固定，session 内不能改 → **做不到 cc 的 turn 级重组**
- 但 **buildSystemPrompt 在每次创建 session 时被调**（chat 首建/worker/rotation/group）→ **"创建时按阶段选配"可行**
- **轮转（rotation）重新调 buildSystemPrompt** → **"轮转时按新阶段重拼"可行**
- turn 级按需由 **skill 机制**承担（description 匹配 → Read SKILL.md）

**借鉴 cc 的机制**（claude-code-analysis/src/constants/systemPromptSections.ts）：
- section 数组 `{ name, compute }` 化 + 按场景组装 + memoized 缓存（cacheBreak 控制重算）
- EM 可借鉴其"section 化 + 按场景组合"，但缓存机制（prompt caching 省钱）受 Pi 约束价值有限——EM 主要是**组织 + 场景聚焦**收益

---

## 一、设计目标

1. **常驻最小化**：只留每个场景都要守的核心规则，减少注意力稀释
2. **场景聚焦**：当前阶段的规则最新鲜、最靠前、最全
3. **可维护**：section 独立常量，改一处不影响整体
4. **轮转自动适配**：阶段变化后，轮转重拼自动用新阶段组合
5. **兼容**：用户在设置里自定义的提示词行为不变

---

## 二、Section 拆分（prompts.ts 重构）

把 MINT_SYSTEM_PROMPT 拆成独立常量。**不直接改 MINT_SYSTEM_PROMPT 字符串**，新增 SECTION_* 常量并存（MINT_SYSTEM_PROMPT 保留给 system-prompt-manager 用，见第五节兼容）。

| 常量 | 对应段 | 内容 | 常驻/选配 |
|------|--------|------|-----------|
| `SECTION_IDENTITY` | identity | Mint 角色（项目经理+架构师） | 常驻 |
| `SECTION_LANGUAGE` | language | 中文交互 | 常驻 |
| `SECTION_EASYMINT` | easymint | 项目生命周期、三角色（你想/Builder写/Evaluator验） | 常驻 |
| `SECTION_GUIDE_USER` | guide_user | 操作向导、对话节奏 | 常驻 |
| `SECTION_SYSTEM_MESSAGE` | system_message | 系统消息分类 + 注入防护 | 常驻 |
| `SECTION_UI_TOOLS` | ui_tools | 8 个 UI 工具清单 | 常驻 |
| `SECTION_RULES_CORE` | rules 前半 | 授权范围/行事风格/非程序员适配/自我约束/输出规范 | 常驻 |
| `SECTION_CREATION_FLOW` | creation_flow | 创建引导（双因子/五步/两入口/7Gate/触发 skill） | **选配（引导期）** |
| `SECTION_RULES_EXECUTION` | rules 后半 | 任务执行详规：决策树/委派/task.json 流程/run.json/中断恢复/文档规范/长命令 | **选配（开发期）** |

**常驻组合**（每场景必注入，~110 行）：IDENTITY + LANGUAGE + EASYMINT + GUIDE_USER + SYSTEM_MESSAGE + UI_TOOLS + RULES_CORE
**常驻量对比**：现状 252 行 → 常驻 ~110 行（减 56%）

## 三、按阶段装配

### 3.1 阶段判断

新增 `detectProjectStage(projectPath)`（放 prompt-sections.ts）：读 task.json 判断。

```typescript
export function detectProjectStage(projectPath: string): "guidance" | "development" {
  // 读 <projectPath>/task.json
  // 无文件 / tasks 为空 / 所有 title 含 "{{"（占位符）→ guidance（引导期）
  // 否则 → development（开发期）
}
```

**判断依据**：新建项目 task.json 是占位符（如 test2 的 `{{TASK_TITLE}}`）或无任务 → 引导期；项目初始化/开发后产生真实任务 → 开发期。

### 3.2 各阶段注入组合

| 阶段 | 常驻组合 | 选配 section |
|------|---------|-------------|
| **引导期（guidance）** | 常驻组合 | `SECTION_CREATION_FLOW` 完整 + `SECTION_RULES_EXECUTION` **极简骨架**（只留"委派分工总则 + 小微修改决策树"，不含 task.json 执行/run.json/中断恢复细节） |
| **开发期（development）** | 常驻组合 | `SECTION_RULES_EXECUTION` 完整 + `SECTION_CREATION_FLOW` **省略**（需求变更走 ui-sync/requirement-breakdown skill，不需要创建引导） |

**"宁多勿缺"原则**：阶段判断不确定时倾向注入完整版（如开发期也保留 creation_flow 极简骨架，防漏）。开发期省略 creation_flow 完整细节，因细节在 creation-guide skill 按需加载。

### 3.3 组装函数

```typescript
// prompts.ts
export function assembleMintPrompt(stage: "guidance" | "development"): string {
  const core = [SECTION_IDENTITY, SECTION_LANGUAGE, SECTION_EASYMINT,
                SECTION_GUIDE_USER, SECTION_SYSTEM_MESSAGE, SECTION_UI_TOOLS, SECTION_RULES_CORE];
  const stagePart = stage === "guidance"
    ? [SECTION_CREATION_FLOW, SECTION_RULES_EXECUTION_BRIEF]
    : [SECTION_RULES_EXECUTION];           // 开发期省略 creation_flow
  return [...core, ...stagePart].join("\n\n");
}
```

### 3.4 buildSystemPrompt 改造（agent-service.ts:508）

```
buildSystemPrompt(projectPath, isDesigner):
  designer → DESIGNER_AGENT_PROMPT
  否则 →
    stage = detectProjectStage(projectPath)
    effective = resolveEffectivePrompt()      // 用户在设置里选的提示词
    if (effective 是 builtin 默认) → assembleMintPrompt(stage)   // builtin 走按需装配
    else → effective（自定义整串，行为不变）
    + skills 段 + env 段 + profile 段（不变）
```

**session 内阶段变化不重组**（Pi 约束）——但**轮转时重拼**（rotation.ts:100 已调 buildSystemPrompt，阶段判断生效后自动按新阶段重组）。新建 session 也按当时阶段拼。

## 四、常驻 vs skill 分层清单

判定原则：**"每个场景都要守"→ 常驻；"只在某场景用到"→ skill**。

| 规则 | 归属 | 现状 |
|------|------|------|
| identity/language/system_message/注入防护/授权 | 常驻 | ✓ 已在常驻 |
| easymint 生命周期/三角色 | 常驻 | ✓ |
| 渲染正确性自查 | skill | ✓ creation-flow-prototype |
| 成本映射/场景判定 | skill | ✓ cost-map/scenarios |
| 五步话术/原型分级 | skill | ✓ creation-flow-* |
| 需求拆解/方案先行 | skill | ✓ requirement-breakdown/plan-first |
| **task.json 执行流程/run.json/中断恢复/文档规范/长命令** | **开发期选配**（下沉 SECTION_RULES_EXECUTION） | ⚠️ 当前常驻 rules 后半 |

## 五、system-prompt-manager 兼容

**矛盾点**：manager 允许用户在设置里选/编辑自定义提示词（整串），`resolveEffectivePrompt()` 返回当前默认。拆 section 后如何兼容？

**方案**：
1. **保留** `MINT_SYSTEM_PROMPT` 整串导出——manager 的 `BUILTIN_DEFAULT_PROMPT_STRING` 继续用它（用户可见/可切换的"完整版"）
2. **新增** `assembleMintPrompt(stage)`——buildSystemPrompt 在 **builtin 路径**走按需装配
3. **自定义提示词**（用户新建的非 builtin）继续"整串 + 动态段"，行为不变
4. 判定 builtin：effectivePrompt 的内容等于 MINT_SYSTEM_PROMPT（或 defaultPromptId === "builtin-default"）→ 走 assemble；否则用整串

**风险**：用户自定义提示词享受不到按阶段装配（整串）。可接受——自定义是用户全权，且动态段（skills/env/profile）仍追加。

## 六、轮转重拼与就近重申

### 6.1 轮转重拼（自动生效，无需改 rotation）

`rotation.ts:100` 已调 `buildSystemPrompt(chat.projectPath, ...)`。detectProjectStage 生效后，**轮转自动按当前阶段重组**——引导期创建的 session 若在开发中触发轮转，重拼出的新 prompt 就是开发期组合（creation_flow 省略、执行规则完整）。

### 6.2 就近重申（对抗淡化）

在关键系统消息里重申核心规则，事件触发时规则新鲜：
- **handoff prompt**（rotation.ts:86）：摘要后加"当前阶段关键规则"一句话（如开发期重申"任务状态由系统回写、不手动标记"）
- **委派系统消息**：委派 Builder 时重申"只实现 taskId 任务、不改其他任务状态"

### 6.3 轮转重述关键规则

handoffPrompt 的"请检查项目当前状态"后可附当前阶段的核心 Gate/规则摘要（1-2 行），让新 session 开局就记住当前阶段重点。

## 八、风险与缓解

| 风险 | 缓解 |
|------|------|
| 阶段判断不准（task.json 判断边界） | 宁多勿缺：判断不确定时注入完整版；常驻保底核心规则 |
| session 内阶段变化不重组 | 轮转重拼兜底；冗余无害（引导期规则留在开发期不矛盾，只是冗余） |
| 自定义提示词不受按阶段装配 | 接受；动态段仍追加 |
| 拆分破坏 builtin 编辑 | MINT_SYSTEM_PROMPT 整串保留，manager 行为不变 |

## 九、待确认

1. **阶段判断数据源**：task.json 读真实任务判断。是否有更准的信号（如 project.status：setup/development/completed，project-service 有）？——task.json 直接读文件最独立，project.status 需传 store。倾向 task.json。
2. **开发期是否完全省略 creation_flow**：完全省略（细节在 skill）还是保留极简骨架（防中途回到引导）？——倾向保留极简骨架（"创建引导走 creation-guide skill"一行）。
3. **RULES_EXECUTION 是否再拆骨架/全量**：引导期极简骨架 vs 开发期全量，是否值得再拆一档？——倾向只拆"骨架/全量"两档，不细分。
