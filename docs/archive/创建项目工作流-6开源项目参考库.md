## 二、六个项目反复出现的 7 条共性

1. **用户确认 Gate 是共同主线**——superpowers HARD-GATE、spec-kit 阶段门 + 人审 gate、gstack 逐条 opt-in、mattpocock 前沿等用户答完、BMAD 审查、anthropic 确认唯一性才写码 → **印证 7 Gate 方向正确**
2. **问答设计：一轮一批、带推荐答案**——mattpocock 每题附推荐、gstack forcing questions、spec-kit 选项表 A/B/C → **印证"给选项而非开放问答"**
3. **事实/决策分离，少问**——mattpocock 事实 agent 自查、spec-kit 不确定项限 3 个强迫 AI 不猜 → **印证成本智能引导"禁止无脑抛题"**
4. **What/Why 与 How 分层**——spec 禁技术栈、to-spec 禁文件路径/代码片段、BMAD 五字段契约先锁做什么 → **印证采集阶段不做技术决策**
5. **场景/规模自适应**——BMAD stakes+双路径、superpowers 三路径分类、gstack 模式分叉 → **双因子模型"场景定流程+认知定表达"的现成操作化**
6. **原型按需而非默认**——superpowers visual-companion、mattpocock 说不清的转原型、anthropic ASCII 线框 → **印证原型分级**
7. **产出物落盘可溯源**——gstack Supersedes 溯源链、superpowers spec 落盘 + ledger、BMAD memlog → **印证 Project Profile 落盘方向**

## 五、各项目 agent 精读报告

### 1. Matt Pocock skills（`GitHub/skills/`）

**定位**：mattpocock 的"真实工程"技能包——把工程纪律（对齐、共享语言、反馈环）压成可 hack、可组合的小 skill，插件化交付，对抗"vibe coding"。

**核心机制**：核心原语是 `grilling`：把方案建模成**设计树**，按**轮次**问。每轮只问"前沿"（frontier，所有前提已定的问题），每题附**推荐答案**，等用户答完再算下一轮前沿；**事实由 agent 查（派子代理），决策归用户**；前沿清空即结束。三个入口按场景选：`grill-me`（无状态）/ `grill-with-docs`（有状态，边问边建术语表+ADR）/ `wayfinder`（超大模糊工作，拆成"决策票地图"）。主流程：**grill-with-docs → to-spec（纯综合不采访）→ to-tickets（垂直切片+阻塞边）→ implement**。

**亮点**：
1. 前沿轮次制：一次问完所有可答问题、每题带推荐答案，避免连环追问，且依赖未决的问题自动延后
2. 事实/决策分离：环境事实绝不问用户，大幅降低提问负担
3. 即时共享语言（domain-modeling）：模糊术语当场定义进 CONTEXT.md；ADR 仅"难逆+无上下文难懂+真权衡"三条全满足才写
4. to-spec 的规格模板：Problem / Solution / 极长 User Stories / Implementation / Testing / Out of Scope，明确禁止文件路径和代码片段（易过期）
5. to-tickets 的"迷雾"（wayfinder）：能精确表述的问题才开票，否则记入 Not yet specified，目的地定范围

**对 EM 借鉴**：
1. 需求采集实现为"设计树+轮次+前沿"，每题给推荐选项而非开放问答——最适合非技术用户
2. 事实自动查、决策让用户做：用户资料/技术事实由 Mint 自查，用户只回答"要什么"
3. 边聊边沉淀术语表，规格/工单用统一词汇
4. 完工判据用"前沿清空"而非问题数；说不清的问题（如 UI 观感）转原型/参考图

**精读**：`skills/skills/productivity/grilling/SKILL.md`；`skills/skills/engineering/{grill-with-docs,grill-me,domain-modeling,to-spec,to-tickets,wayfinder,ask-matt}/SKILL.md`

### 2. gstack（`GitHub/gstack/`）

**定位**：YC 总裁 Garry Tan 开源的个人 AI 工程团队——将 Claude Code 变成 23 个专家角色的 slash-command 技能集（office-hours→CEO→设计→工程→QA 评审流水线）。

**核心机制**：每模块是一个 SKILL.md（"决策树骨架"），用**固定数量的一次一个问题**（AskUserQuestion）驱动用户产出可验证证据。office-hours 先按用户身份分「Startup 强制追问模式/Builder 共创模式」，用 6 个 forcing questions（需求真实性/现状替代/具体用户/最小楔子/观察惊讶/未来适配）逼出具体答案；plan-ceo-review 以「四种范围模式」（扩张/选择性扩张/守住范围/缩减）+ 每次范围变更逐条经用户 opt-in 的方式评审；plan-design-review 以 7 个 0-10 分维度打分（信息架构/交互状态/情感弧线/AI 味风险/设计系统/响应式/未决决策），逐条补充到计划里。

**亮点**：
1. 角色=提问框架：每个角色是固定视角的问题模板，不是泛泛建议（设计评审用「AI slop 黑名单」11 条硬规则直接判死刑）
2. 证据门槛：反谄媚规则（"interest is not demand"）+ 每次追问二次（第一答通常是包装过的）
3. 评审结论落盘：产出带 `Supersedes` 溯源链的设计文档 + 决策表，供下游 skill 自动消费
4. 跨模型独立评审：Codex/subagent 冷读会话摘要，交叉印证（避免同模型自证）
5. 收尾有"作业"：每次会话给一个具体下一步行动，而非"去实现"

**对 EM 借鉴**：
1. 对话引导内置**强制问题集**（逐条问、不问完整不进入下一步），把"模糊想法"逼成可验证陈述
2. 用**多角色视角轮询**（用户/出资人/设计/工程各自一套问题）替代单一问答，且每条结论需用户确认才入需求文档
3. 需求确认后生成带溯源与决策记录的**设计文档**（含"未被采纳的方案"），供后续开发阶段复用

**精读**：`gstack/office-hours/SKILL.md` + `sections/design-and-handoff.md`；`gstack/plan-ceo-review/SKILL.md` + `sections/review-sections.md`；`gstack/plan-design-review/SKILL.md` + `sections/review-sections.md`

### 3. obra superpowers（`GitHub/superpowers/`）

**定位**：给编码 Agent 用的一整套"头脑风暴→设计→计划→实现"软件开发方法论，由一组可组合 skill 构成（技能在 `skills/*/SKILL.md`），在动任何代码前强制先与人类确认。

**核心机制**：Agent 一启动就被注入 `using-superpowers` bootstrap，自动触发 `brainstorming` skill。请求先被分类为 **spike（探针）/ bounded（小改）/ architectural（架构级）** 三档，每档有不同粒度的产物（聊天内短设计 / 写规格文档），但**批准门槛永不因任务简单而消失**（HARD-GATE）。设计批准后落盘 `docs/superpowers/specs/`，再经 `writing-plans` 拆成 2-5 分钟一粒的任务，用 subagent 逐任务执行 + 两阶段评审。

**用户确认 Gate 节点**：
1. 分类声明后——先说"这属于 bounded，我聊天内给个短设计"，让人能否决
2. 设计分节确认——架构级设计按节展示，每节问"对吗"，再进入写文档
3. 规格自审 + 用户审阅——写完后自检占位符/矛盾/歧义/范围，再明确请用户审阅 spec 文件，说 yes 才进计划
4. 计划文档审阅——计划写完由 reviewer 子代理核对 spec 覆盖度、可执行性
5. 执行方式选择——subagent 驱动 / 内联执行，二选一
6. 每任务两阶段评审——spec 合规 + 代码质量双门；修复循环最多 5 轮，超限由控制器裁定并记入 ledger

**对 EM 借鉴**：
- Gate 不是流程，是原则：把"批准后才动手"做成硬约束，任务再小也要先给两句话设计、等明确 yes——简单任务正是假设最多的地方
- 一次一个问题：多选优先、逐个问目的/约束/成功标准；大项目先拆子项目，每个子项目独立 spec→计划→实现循环
- 规格自审清单（占位符/内部矛盾/范围/歧义）+ reviewer 校准（只拦会导致建错的东西，不吹毛求疵）
- 可视化按需而非默认：mockup/原型仅在"看图比读文更清楚"时才临时提供——对应 EM 的原型确认，避免为所有问题强推原型
- "Spec 是最高权威"：计划与 spec 冲突时以 spec 为准，裁决记录进 ledger，防止实现漂移

**精读**：`skills/brainstorming/SKILL.md`（三路径分类 + HARD-GATE）；`skills/brainstorming/spec-document-reviewer-prompt.md`；`skills/writing-plans/SKILL.md`；`skills/subagent-driven-development/SKILL.md`；`skills/brainstorming/visual-companion.md`

### 4. BMAD-METHOD（`GitHub/BMAD-METHOD/`）

**定位**：开源 Agile-AiDD 方法论，以可安装 skill 形态交付给 Claude Code/Cursor，"决策显式、上下文传递、流程随规模自适应"，同一套方法覆盖周末原型到成熟系统。

**核心机制**：所有实施统一进 `bmad-build`，第一步按影响范围路由——零影响走 One-shot 轻通道，其余走 spec→审查→实现全流程；spec 设 900–1600 token 阈值，超限即拆、不足有歧义；规划深度由需求清晰度定阶梯（清晰直达实施，重大先备 PRD/UX/架构，上游产物只增上下文不改流程）。各 skill 先探测 stakes（hobby/internal/launch）校准严谨度，再选 Fast（[ASSUMPTION] 批量草稿）或 Coaching 引导路径。

**阶段**：Analysis(可选)/Planning/Solutioning/Implementation，产出链式传递（PRD→UX→架构→story→实施）。PRD 定 FR/NFR 与范围；UX 产 DESIGN.md(视觉)+EXPERIENCE.md(行为)，仅 UX 复杂时触发；spec 将任意输入蒸馏为五字段契约（Why/能力/约束/非目标/成功信号）；架构只固定"不变量"并出 ADR。

**亮点**：① memlog 追加式记录+产物从日志派生，多 skill 任意轮转更新零冲突；② Spec Law 八条守契约质量；③ subagent 蒸馏防上下文雪崩；④ project-context.md 沉淀既有项目约定；⑤ bmad-help 按 CSV 目录（preceded-by/required）实时推荐下一步。

**对 EM 借鉴**：① 统一漏斗+影响范围路由=场景定深度；② stakes 校准+Fast/Coaching 双路径即"场景定流程深度+认知定表达颗粒度"的直接操作化；③ token 阈值把流程深度变成可量化判断；④ 五字段契约先锁"做什么"再谈"怎么做"。

**精读**：`src/bmm-skills/ship/bmad-build/step-01-clarify-and-route.md`、`workflow.md`（SCOPE 标准）；`src/bmm-skills/plan/{bmad-spec,bmad-prd,bmad-ux}/SKILL.md`；`docs/zh-cn/reference/workflow-map.md`；`docs/explanation/analysis-phase.md`

### 5. GitHub spec-kit（`GitHub/spec-kit/`）

**定位**：GitHub 开源的「规格驱动开发（SDD）」工具包——让 AI 编码代理先把"做什么/为什么"写成可执行规格，再生成实现计划与任务清单，代码只是规格的产物。

**核心机制**：用 `/speckit.specify → plan → tasks` 三个命令把"一句话需求"逐步精炼为 spec.md（用户故事+验收标准）→ plan.md（技术选型+数据模型+契约）→ tasks.md（按用户故事优先级组织的可执行任务）。模板本身就是约束 LLM 行为的提示词，每个阶段产物落盘成文档并带质量自检清单门。

**亮点**：
1. What/Why 与 How 严格分层：spec 模板明确禁止混入技术栈/API，使规格不随技术变更失效；plan 阶段才做技术翻译（决策+Rationale）
2. [NEEDS CLARIFICATION] 标记机制：限 3 个，配 A/B/C 选项表（含每项影响），强迫 AI 不猜，让非技术用户做关键决策
3. 用户故事按 P1/P2/P3 排序且每故事可独立测试 → 每个故事即一个 MVP 切片，任务按故事分组，MVP 先行、增量交付、每阶段有 checkpoint
4. 任务格式规范化：`[ID] [P?] [Story] 描述+精确文件路径`，标并行任务、画依赖图，任务可直接交给 LLM 执行
5. 宪法（不可变原则）+ 阶段门 + 质量清单：simplicity/anti-abstraction 等 gate 内嵌模板，复杂度须书面证成；workflow.yml 里 spec/plan 之间还有人审 gate

**对 EM 借鉴**：
1. 对话采集阶段用模板强制抽象层 + 不确定项显式打标（≤3），用选项表让用户拍板而非 AI 猜——正合非技术用户场景
2. 先产出"用户故事优先级清单"再做任务，任务按故事分组，MVP 只做 US1，天然支持逐步确认
3. 任务条目强制"ID+并行标记+所属故事+文件路径"，保证生成清单可直接被 Builder/Evaluator 执行
4. 每阶段（需求→计划→任务）用质量 checklist 做门，满足才放行下一步

**精读**：`spec-driven.md`；`templates/spec-template.md`、`plan-template.md`、`tasks-template.md`；`templates/commands/{specify,plan,tasks}.md`；`templates/constitution-template.md`；`workflows/speckit/workflow.yml`

### 6. Anthropic skills（`GitHub/anthropics/skills/`）

**定位**：Anthropic 官方开源的 Agent Skills 技能库——每个技能是一个文件夹 + `SKILL.md`（YAML frontmatter + 指令正文），Claude 按需动态加载，把专业工作流教给 Agent。

**核心机制**：`frontend-design` 不是工具脚本，而是「设计总监角色注入 + 两遍工作流」。先让 Agent 把 brief 落地为具体主题/受众/页面单一职责；再产出四件套 token 系统（4-6 个 hex 色、2+ 字体角色、ASCII 线框布局概念、签名元素）；写码前对照 brief 批判去模板化、确认唯一性后才动手，写码后截图自审。

**亮点**：
1. 写码前必产「token 系统」四件套，作为写码唯一依据，所有颜色/字体决策从它派生
2. "两遍工作流"：先 brainstorm 设计计划 → 对照 brief 批判 → 确认唯一性才写码
3. 明示 3 种「AI 默认风格」反模式清单，教 Agent 识别并绕开模板化
4. 签名元素（signature）：大胆只花一处，其余克制，抵消 AI 生成感
5. 用 ASCII 线框做低成本原型对比；写码时提醒 CSS 选择器优先级互相抵消、构建中截图自审

**对 EM 借鉴**：
1. 原型 Gate 可直接落地为「token 系统四件套」——Agent 先交色板/字体/布局线框/签名元素，用户确认后再写码
