# 如何让 AI 更稳定地做好 UI

整理日期：2026-10-24。来自 Em 的实际迭代复盘，属于工作方法建议，不是经过实验证明的通用定律。

## 先建立共同的视觉目标

“高级、丝滑、通透、精品”表达愿望，但不能单独充当验收标准。AI 需要把愿望变成可观察的条件，并主动找参考和已有实现，而不是把搜集资料的任务重新交给用户。

每个局部任务先写清：使用场景、必须保留的布局和色系、一份主参考、几项明确特征、不可接受的效果。例如：导航基色稳定；背景在玻璃内可辨；细线穿过边缘时发生可见弯折；不能出现厚白圈；文字与按钮可读。

主参考用于定方向，其他参考只解决具体问题。不要从多个作品各取一种装饰，最后拼成没有统一语言的页面。

## 优先复用真实实现

遇到材质、图表、富文本、动效这类成熟能力，先搜索可运行的开源作品，检查核心源码、实际演示、许可、依赖和适配成本。区分“有源码”“许可可复用”“能在目标环境运行”“实际效果合适”四件事。

能合法复用成熟组件时，优先保留其有效实现再适配，而不是读完 README 后按印象重新仿造。若决定自研，要指出现有方案无法满足的具体要求。

## 从小样确认，再扩大到完整页面

先用一个组件、真实内容和完整状态验证视觉方向。玻璃先验证一个胶囊与一个选中指示；聊天先验证一轮完整消息；弹窗先验证最复杂的一步及切换。局部成立后再延展布局和组件体系。

小样也要体现实际应用中的密度、中文、长内容、滚动和选中状态。纯展示大卡片成立，不等于高密度应用控件成立。

## 用受控对比替代反复猜测

- 固定截图尺寸、缩放、背景、内容和位置，原版与候选并列展示。
- 一轮只改变一个因素组，例如曲面与折射，或反光与阴影；别同时重排布局、改色、换字体。
- 保存用户认可的版本作为基线。候选没有胜过基线时，不自动晋升为新基线；用户否定后停止沿同一路径叠加。
- 动态效果提交状态序列或可运行演示，检查启动、跟随、释放、打断和恢复，而不只检查终点截图。

## AI 必须完成视觉检查

代码写完、测试通过不是视觉工作结束。应在目标浏览器或应用里观察最终计算样式与实际画面，定位到原因：是参数未生效、背景采样不对、层叠遮挡，还是视觉方案本身不成立。

分开记录三种结论：工程验证通过；视觉上有哪些可见变化；哪些仍需用户主观判断。不能用“57 项测试通过”替代“材质满意”的证据，也不要把普通近似公式称为已经复刻原生渲染。

## 控制 AI 常见的退化

| 常见退化 | 对应做法 |
| --- | --- |
| 把“存在感”理解为增加边框和阴影 | 先分辨是层级、明暗传递、尺寸还是材质关系不足 |
| 局部每项都增强，整体越来越吵 | 回到页面主次关系，每次只强化一个重点 |
| 一套圆角卡片套全部风格 | 从真实用途、排版、密度、组件结构和互动建立差异 |
| 参数变了就声称有效 | 检查浏览器最终计算值、真实背景及实际截图 |
| 持续修补不合适的路线 | 在同条件下复现成熟候选，用可见差异决定换路线 |
| 用户不停帮 AI 做肉眼验收 | AI 先完成自检，带着具体差异和证据请用户判断方向 |

## 适用于 Em 的任务约定示例

> 保留现有布局和色系。先查找有源码和可运行演示的成熟参考，说明适配差异。先制作一个局部对照小样，使用相同背景、尺寸、内容和状态。将现有版本与候选并列，保留用户认可的基线。视觉方向成立后，再扩展为可复用组件并接入正式页面；同时验证交互、可读性、性能与项目导出。报告时区分功能检查和视觉判断。
