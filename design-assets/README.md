## 当前为什么仍会出现“仿造”

现有链路已经将 visual-spec.json、theme.css、components.css、runtime.js、gallery.html、4 类 HTML 页面和 native-tokens.json 写入项目，并要求 Agent 复用。它不是只有颜色提示词。

不足在于：风格预览的 React 代码、共享 HTML 文档渲染器、生成项目所选框架组件，没有统一成为一套可安装并导入的组件实现。规则描述和 CSS 配方不能完整表达组件结构、组合方式与交互行为。即使读到了 CSS，模型仍可能重新搭结构、重写菜单或用近似效果替代素材。原生平台当前也主要是 Token 与移植说明，不能据此承诺已有相同组件。

## 建议的升级单位：可运行的风格组件包

每套正式风格包至少包含：

- 可直接复用的组件源码、样式、必要 SVG/纹理/字体与依赖清单。
- 明确的材质、排版、密度、轮廓、导航、图表及动效规范，不只提供一组颜色。
- hover、pressed、focus、selected、disabled、loading、error，以及浮层/空态等完整状态。
- 一个组件展示页与真实任务页面，预览直接导入包中的组件，不另写一份更漂亮的演示。
- 包版本、源文件哈希、组件 ID、来源/许可/署名、支持平台与回退规则。

选择风格后按目标技术栈安装匹配的源码和必要素材；模型主要做内容、数据与业务组合。缺少组件时走明确的补充实现流程，不允许悄悄替换成未经验证的近似组件。已有项目锁定包版本；升级必须保留用户改动，延续现有 manifest/事务保护。

可参考 shadcn registry 的源码分发格式：files、依赖及目标路径可以一起安装。这里推荐借鉴分发机制，不是把所有风格做成同一种 shadcn 默认外观。共享无样式交互底层可以复用焦点、键盘和菜单行为；风格结构与材质仍需专门设计。

官方参考：
- https://ui.shadcn.com/docs/registry/registry-item-json
- https://www.radix-ui.com/primitives/docs/overview/introduction

## 美术升级与验收

先给首批 6 个方向做同一组真实任务：工作台/列表、详情、设置表单和弹窗。用一致的业务内容比较，检查隐藏风格名称后是否仍能分辨其语言。不能通过换标题、换主色或换装饰主视觉假装完成风格区分。

先从 2 套建立预览与项目同源的完整链路，再扩到 6 套；首批建议极简 + Material 验证通用组件链路，再补玻璃或黏土验证材质扩展。保留现有 17 个方向，但未打磨项标注基础/实验，不能都宣称精选。

首批打磨核心范围为按钮、输入、选择、菜单、导航、列表/表格、弹窗/抽屉、反馈/空态，再补符合实际项目的业务区块。验收同时看源代码确实导入了选定组件、实际交互、代表性尺寸截图与性能；不能只检测 class 名或提示词。

优先支持 Web/Electron 的明确技术栈。Vue、小程序、Flutter、SwiftUI、Compose 等需要分别提供适配组件或明确标注暂不支持，不能让 CSS Token 自动变成跨平台保真承诺。

## 将来的 Em 素材库

建议展示分区为产品风格、组件、业务区块、展示动效、图形/字体素材。一个资产可带多个用途标签，但动效场景不能自动晋升为整套 UI。每项记录来源、版本、许可、平台、预览、可安装状态、性能档位及依赖大小；未取得源码的参考只能展示为参考，不能显示“直接使用”。

研究资料当前在被 Git 忽略的 private_docs/ 中（原 docs/，2026-10-26 改名）。清单可以进入版本管理，但别的开发机不会自动获得这些本地资料。正式入库时应按来源与许可逐项转入正式资源目录，保留归属，不把整套动效依赖或品牌素材全量塞进应用。
