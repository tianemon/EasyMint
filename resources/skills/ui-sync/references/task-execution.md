# 正式任务执行与恢复

仅当本次工作有对应的正式任务清单时使用；无清单不补建。执行方式沿用内置核心的协作原则：默认亲自推进，交接确有收益时才委派。

task.json 执行流程（你作为进度监控者）：

**你是进度监控者，不是状态机执行器。** task.json 的 status 只是辅助快照（可能滞后或缺失），以实际改动和验证证据判断该重做/验收/跳过。首次接手、丢失上下文后恢复或发现状态矛盾时，定向核实任务、记录、代码及失败证据；同一任务连续执行时沿用仍有效的证据，只补变化或缺口，不每轮重读整套资料。

task.json 有未完成任务 + 用户说「继续」「执行」「开始」等指令：
1. 按上述进度核实规则定位当前任务；需要恢复上下文时先读 task.json 与开发记录快照，再按缺口读相关明细、git diff、代码和已有失败证据。旧 escalation.json 若存在且相关，可作为历史来源核实，不要求新建或等它出现，也不只看 status 字段
2. 按依赖顺序找下一个未完成的任务（以你核实的真实状态为准，status 字段仅供参考）
3. 调 set_task_status(id, "building") 通知 UI 开始编码
4. **按「执行方式」推进——先判委派还是亲自，不要默认委派**：
   - **委派**（交接收益明确）：用 task 工具选择实际可用的实现模板（内置为 default-builder），**taskId 参数传本次任务 id**，并补齐必要背景与范围。执行方按 id 读取真实任务详情；任务标记 tdd: true 时先确认有效的失败用例，再实现到通过。按实际工具能力检查引用点、影响范围和适用测试，不把某个可选分析工具当作前置条件
   - **亲自**（默认方式，或交接收益不足）：你直接读 task.json 取该任务详情动手实现——主会话已握有全部上下文，拆出去反而多一轮交接
5. 实现完成 → 按本次交付风险、项目约定和实际能力核对改动与验证证据，明确未验证范围；满足独立复核场景时才交验收模板（内置为 default-evaluator）：当前正式任务仍为 building 时，可进入 evaluating 并传 taskId；委派结果已自动进入终态时，做临时独立复核，不仅为复核回退原任务状态或新建 task.json。亲自实现的自验/必要复核通过后标记 done；委派结果的自动回写规则保留，但状态已完成不等于免除你对结果的核实
6. 核实是否达到任务完成标准：亲自实现的按工具契约收尾，委派的保留系统自动回写；记录真实结果与未解决问题，按项目约定更新开发记录，再进入步骤 7。
7. 回到步骤 2 继续下一任务
8. 失败时先核对原因、已做尝试和剩余权限；有依据且仍在授权范围内才重试，不因固定次数继续盲试或创建升级文件。执行方通过现有委派结果交接原因、证据、未解决事项和所需决定；主会话据此推进可独立处理的部分，必要时向用户说明取舍。**委派实现的 failed 由委派结果自动回写，不重复手动标记**；用户暂停或中止时停止相应工作，不自动重启
9. 全部完成后按项目约定维护必要文档并简要总结；仅交付确需可复用运行入口或已有运行方式变化时，按 project-run 技能增量维护 .easymint/run.json。已有正确配置不重写，配置入口不等于获准执行
