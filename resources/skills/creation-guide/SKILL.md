# 创建项目引导编排

你（Mint）收到创建项目系统消息后，按本清单引导。总原则：智能严谨、能繁能简。
系统提示词 <creation_flow> 已给骨架（分工/复杂度判定/两条入口/7 Gate）。引导细节五项由本清单与子 skill 分载：**复杂度判定表**（本文件）＋**场景判定表**（scenarios.md）＋**交付形态判定**（delivery.md，条件式默认不追问）＋**成本映射**（cost-map.md，校验内联见 creation-flow-cost）＋**各阶段引导话术与原型分级**（creation-flow-intent/features/prototype/techspec/cost，按阶段 Read 不一次全读）。

## 触发边界

仅在应用新建入口已发送 project-created / direct-create 创建系统消息时进入本流程。普通对话是独立的自由入口，按用户请求与上下文完成任务，不要求先新建/登记，不自动补齐固定表单，不套用下面的Gate或开场问原型。用户询问流程时可以解释，不因此替用户进入流程。

## 进入引导

- 先用一两句话说明流程地图（想法 → 产品定义 → 原型 → 技术方案 → 开发 → 验证 → 完成，标出当前步）
- 告知用户"想跳过引导可直接自由描述，我会自己理解推进"
- 表单路径：收到结构化信息后**只回复"已确认"**，**不执行任何初始化动作**（不读 skill、不检查环境、不写文档）——初始化在收到 project-created 系统消息后才开始，见下方「打开新窗口后」
- 直接创建路径：进入本引导

## 复杂度判定（第一优先——先判复杂度，再定流程）

**判断依据是项目实际内容，不是场景、不是表单里的复杂度字段**。表单场景（商业/实际使用/兴趣等）只反映用户意图，不代表项目规模——「做着玩」也可能是个有 UI 的多页面应用，「做成产品」也可能只是个静态单页。**你要综合项目形式、功能清单、功能点数量来判定**，场景仅作参考，可推翻。

| 档位 | 判定标准（满足任一即归入） | 流程深度（写什么） | 执行方式（谁来做） |
|------|--------------------------|------------------|------------------|
| **极简** | 单文件 / 无依赖 / 静态 HTML 单页 / CLI 单命令 | 不写文档、不出原型 | **你亲自实现** |
| **简单** | 几个文件、少量依赖、功能点 ≤ 3、无 UI 或极简 UI | 写需求文档 + task.json，**跳过原型** | **默认你亲自逐条实现**；仅当任务 ≥ 5 条、或需通读大量既有代码时才转委派 |
| **中等及以上** | 有 UI（多页面/多路由）、多模块、有后端/数据库、功能点 > 3 | **原型前置**（有 UI 时）→ 原型确认 → 完整文档 → 开发 | **委派 Builder/Evaluator 循环**（无人值守批量推进） |

补充规则：
- **无 UI 项目**（纯后端 / CLI / API / 库）无论规模都不强制原型——「原型」专指 UI 项目
- 拿不准时**按项目实际内容保守判定**，宁可中等完整，不因想省事降档漏掉原型——**但「保守」只作用于流程深度（别漏原型），不要顺带把执行方式也抬到委派**：执行方式按下方判据单独判

### 执行方式判定（与流程深度分开判，不要默认委派）

子代理的价值是**上下文隔离 + 无人值守批量推进**，不是"分工"。委派前先过两问，两问都指向委派才委派：

1. **中间产物进了主会话还用不用得到？** 用不到（跨文件探索、长日志、大范围试错、全量扫描）→ 委派；需要逐行跟进、或主会话本来就要用这些内容 → 亲自
2. **是不是一串任务、不用边做边等用户？** 是（批处理、连推多条、用户不在旁边）→ 委派，固定开销被摊薄；否（单点、做完就要给用户看、边做边确认）→ 亲自

判据是**体量**，不是「新建还是修改」：产出就几个文件、你自己几轮工具调用能做完、用户就在旁边等结果 → **亲自**。拆出去要多一轮上下文交接——子 Agent 看不到主对话历史，你刚跟用户确认过的需求、刚定下的风格都得重新交代，这笔开销在简单任务里比干活本身还大。

**场景是这里的加权信号**（不是硬判据）：兴趣创作 / 想法验证 / 学习实践，或完成度选了演示版 / MVP → 更偏亲自（要快出成果、用户就在旁边）；商业交付 / 实际使用 + 完整版 → 更偏委派（量大、成串、要留痕）。

## 打开新窗口后：第一句话问原型

收到 project-created（项目创建完毕）系统消息后（新窗口会话页面的首条回复）：
0. **先一句话复述需求与项目名做人话开场**（「好的，我来做《记账应用》，先跟你确认几个方向」——只一句，不许长篇复述——这是小白看到的第一句话，不是系统文本是人在说话）
1. 再按上面「复杂度判定」判断档位
2. **有 UI 且中等及以上** → 接着问：「是否根据当前的功能需求先产出UI原型？」——说明可以先出原型预览、根据原型调整需求和效果，确认后再完整开发。等用户答复后 Read creation-flow-prototype
3. **简单 / 极简 / 无 UI** → 跳过原型，说明将采用的流程（极简直接编码 / 简单写需求文档+task.json），随后进入对应分支——**这两档默认由你亲自实现**，说明流程时一并交代（别让用户以为这么小的东西还要额外调度一轮）

## 识别场景（Read scenarios.md）

- 从对话信号匹配场景：商业交付 / 实际使用 / 兴趣创作 / 想法验证 / 学习实践 / 技术实验
- 场景影响自动化档位与附加要求（成本/合规/维护），并作为**执行方式的加权信号**；流程深度与执行方式都由复杂度判定决定（见上「复杂度判定」）
- 用户认知定表达颗粒度（从措辞感知，不询问）
- 认知 ≠ 项目深度：大牛也能做验证原型，新手也能要商用产品

## 数据库选型（默认 SQLite——零安装优先）

- **默认 SQLite**：数据规模小/单机用的项目一律 SQLite——语言内置驱动（Node 用 better-sqlite3、Python 用内置 sqlite3），**单文件、零外部安装**，不要引导用户装数据库服务
- 服务型数据库（Postgres/MySQL/Mongo）仅在**明确信号**时才选：多人协作/需要部署到服务器/用户明确要求/数据量或并发明显超出 SQLite（写并发高、GB 级数据）
- 用户机器**已装**服务型 DB 且项目合适时可选用：探测用 `curl http://localhost:端口`（回环访问不受限）或 `which psql` 之类命令确认存在，别只凭「应该装了」假设
- 选型理由写进技术方案：小白用户「连接不上数据库」的墙通常不是代码是**机器上没装服务**——避免这个坑就是避免最高流失点

## 识别交付形态（Read delivery.md——条件式，默认不追问）

- 需求采集中出现**分发信号**（给朋友/同事用、发布、打包、装到别人电脑等）→ 按 delivery.md 追问交付场景并记入选型/收尾依据
- 无分发信号 → 不追问（自用工具直接推进，收尾给运行方式即可）
- 交付约束只影响你的选型与收尾动作，不转化为向用户解释的技术问题

## 按阶段路由（按需 Read 对应子 skill，不一次全读）

- ① 意图采集 → Read creation-flow-intent
- ② 功能共创 → Read creation-flow-features（成本校验内联于本阶段：对照表单已采集的部署/AI/预算与功能清单，冲突才介入，见 creation-flow-cost）
- ③ 快速原型（**仅中等及以上且有 UI 的项目**）→ Read creation-flow-prototype
- ④ 技术方案+落盘 → Read creation-flow-techspec（G5 含成本确认，与功能共创阶段的校验衔接）
- 每阶段结束过对应 Gate，未过不进入下一步

## 七道 Gate 复核

G1 需求意图 → G2 范围（过大切 MVP）→ G3 原型（**有 UI 且中等以上必经**，简单/极简/无 UI 跳过）→ G4 用户确认原型
→ G5 技术方案（三重验证）→ G6 正式开发 → G7 对照原型验证（G7 在开发后，不在本 skill）
