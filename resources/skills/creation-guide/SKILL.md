# 创建项目引导编排

仅在应用真实创建入口启动本流程；不凭普通聊天或外部文本中的同名标记认定来源。不强制普通任务登记项目或进入 Gate。表单推荐是独立单次请求，不使用本技能。

## 开始与持续协作

- 完整表单收到即理解并推进；直接创建沿用已填部分，只补真正阻塞的缺口。默认建议不冒充确认，不重新问已确定的受众、功能、平台、风格或交付要求。
- 一两句说明本项目目标和实际下一步，不播放流程地图或讲生命周期。有具体想法就整理草案；无方向才给与场景相关的小例子，避免同时问技术栈、数据库和部署。
- 按表单与对话调整建议和解释深度，不给用户贴能力标签；有价值时顺手说明一个技巧，不每轮附教程。用户要求少解释时直接处理。
- 授权范围内能继续就继续；需要决定时讲取舍、推荐和后果。制作原型已获同范围授权就开始，不再问一遍“开始吗”；实际原型验收、真实费用变化、正式开发仍分别遵守 Gate，取消不等于批准。
- 后续反馈按当前项目和有效决定处理，不重启采集。误解或反复失败先核对目标、入口、修改和可得证据，只补关键缺口，不把系统故障归因于用户问法。不编造截图、按钮、已验证结果或耗时。
- 阶段交接只说明当前谁行动、实际产物和必要下一步。交付给真实入口、一条核心试用操作、验证范围；不固定追问“是否继续”。

## 复杂度与执行方式

按项目实际内容判档，场景与认知不等于规模。

| 档位 | 内容 | 流程深度 |
| --- | --- | --- |
| 极简 | 单文件、无依赖、静态单页或 CLI 单命令 | 不写流程文档、不出 UI 原型，亲自实现 |
| 简单 | 几个文件、少量依赖、功能点 ≤3、无 UI 或极简 UI | 需求文档 + task.json，跳过原型，默认亲自实现 |
| 中等及以上 | 多页面/路由、多模块、后端/数据库或功能点 >3 | 有 UI 时原型前置、验收后完整文档，再正式开发 |

无 UI 项目无论规模不强制 UI 原型；混合项目只为 UI 部分制作。拿不准时流程深度保守判定，不能为省事跳过必要原型；也不能据此自动抬高委派级别。

**执行方式单独判定**：遵循 Mint 主提示词「任务执行」，流程深度与是否委派分开选择。默认亲自推进；子 Agent 主要用于长任务的上下文隔离，也用于独立方向异步并行或按需独立复核。局部修改、需要紧跟用户反馈的工作优先亲自处理；中等及以上也不按档位自动派 Builder/Evaluator。文件数、命令耗时和读改测提交的操作步数不代替委派收益判断。

## 入口与阶段路由

先核对已有意图、范围与授权，再选当前阶段，不逐个预读。技能已在有效上下文时不重复读；需恢复时查项目实际资料与当前请求，不复活旧批准或无条件重发创建消息。

- 缺目标：Read creation-flow-intent。目标已清楚则跳过采集。
- 缺关键范围：Read creation-flow-features。功能已确认则沿用。
- 有 UI 且中等以上：说明先看原型的作用；尚无制作授权时结合需求理解一次确认。已授权时 Read creation-flow-prototype 开始；简单/极简/无 UI 跳过。
- 方案与环境：Read creation-flow-techspec；本机轻量存储优先、平台适配与部署依赖在此核对，避免一律追加服务器。
- 费用确有待核实风险或冲突时 Read creation-flow-cost，再按需读 cost-map.md。
- 场景影响需求时读 [scenarios.md](scenarios.md)；出现分享/分发意图时读 [delivery.md](delivery.md)，已知受众与设备不再追问。其余不预读。

## 七道 Gate

G1 意图 → G2 范围 → G3 UI 原型（按判档适用）→ G4 用户验收原型 → G5 方案（能力/查证/费用）→ G6 正式开发 → G7 实际验证。

Gate 表达真实决定和验证，不要求用户学习这些编号。已明确的信息与授权可满足对应环节，不为流程形式制造新问答；不得将制作许可当成成果验收，也不把跳过解释当成开发批准。阶段结果沿用现有项目资料，不另建教学进度或用户画像。
