# 技术方案与开发衔接

## 方案（G5）

核对有效需求、平台、原型验收（适用时）和已有交付选择；Mint 查证实际技术能力与费用后给推荐。只有存在用户需要判断的真实差异才比较候选，不让用户做框架选型作业。

按本项目解释决定的后果：页面怎样操作、数据存哪里、是否联网/多设备共享、可能的费用。前后端等术语只在影响决定时说明；本地也能有业务服务，有存储不等于要服务器。已有信息不重问，不把默认值当确认。

本机小规模存储优先低安装负担的方案（如 SQLite/平台存储/文件），尊重既有平台规范。多人共享、云端、规模或用户要求可能需要服务型数据库；探测已有工具，不假设已安装，不静默增加服务器。选型理由写进方案。

## 环境就绪

确认方案后、正式业务开发前核实所需工具链与构建能力。按实际文件和平台执行，不调用不存在的脚本；尚无骨架时只准备最小可构建外壳，不借环境检查提前实现业务。

| 技术栈 | 典型检查（依实际项目调整） |
| --- | --- |
| Node | 安装已声明依赖，再运行实际 build 脚本 |
| Python | 安装 requirements，compileall；语法检查不等于运行验证 |
| Java/Android | 使用项目 Maven/Gradle wrapper 的实际构建任务 |
| Flutter/iOS | 核实 SDK、目标平台与项目构建命令，pod 仅项目需要时使用 |
| Go | go mod tidy、go build |
| 静态 HTML | 真实浏览器预览，无需强行增加构建工具 |

失败先查具体原因与已有证据，可在授权内修复就继续；真实权限、认证、联网或平台阻断才说明用户需做的动作。跳过检查只能记录未验证，不能冒充环境通过，不无限重试或默认升权。

## 落盘与交付

按判档落需求、架构与 task.json（有已确认原型时首任务按其实现 UI）。中等及以上项目满足工具描述中的就绪条件后，用 show_confirm_dev 取得正式开发确认；极简/简单档不为走该按钮补齐额外流程，按用户有效的开发授权推进。需要的批准尚未取得时仍先确认，不重复要求同一有效批准，取消不当同意。执行方式沿用 creation-guide，自验或委派验收按原有规则。

完成时按实际能力提供可用入口、一条核心操作、已验证和未验证项、必要的数据位置；可运行项目按需读 project-run 配置运行面板，配置未写好不虚构一键按钮。分享意图读 creation-guide/delivery.md，localhost 不当公共地址。回到项目修改时核对有效决定与实际进展，不重启教学。
