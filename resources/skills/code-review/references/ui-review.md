# UI 风格与交互审查

仅用于审核已实现的页面、共享控件、样式或主题；视觉方案、布局设计和原型构思属于设计阶段。目标是符合该项目已经确认的设计语言，不替项目重新设计界面，也不将某个项目的无边框或自绘要求推广为所有项目的默认规则。

## 先确定项目基准

- 读取当前任务相关的用户要求、项目规则、设计规范、组件库和语义 token；选取现有同类界面作为对照。用户已明确纠正的要求不能被旧组件默认值或旧文档重新覆盖；已有明确例外按其适用范围保留。
- 核对真实使用的控件及其默认参数、全局样式、主题选择方式和最终挂载容器。复用共享组件不代表其默认外观适用于当前页面；项目规范禁止的样式不能因“已有组件这样写”而放行。
- 没有独立设计文档时，从现有同类组件和实际页面提取基准，不凭审查者喜好引入新的视觉方案；冲突只在证据无法消歧且影响结论时说明。

## 必查最终外观与状态

按本次涉及的控件与风险选择实际适用项；无关项跳过，不机械扫描全项目。

| 检查面 | 验收要点 |
| --- | --- |
| 边框与层次 | 容器、菜单、字段、选中态是否遵循项目的描边／无边框约定；同时检查 outline、ring、box-shadow 和伪元素，区分轮廓描边、分隔线及已确认例外。 |
| 控件与原生反馈 | 项目要求自绘的下拉、勾选、单选、数字步进、文件上传入口等是否沿用规定形态；检查原生必填／格式校验气泡、焦点提示和文本框拖拽手柄，不能只搜索 select 或 checkbox 标签。原生 HTML 标签本身不等于未经适配的外观。 |
| 样式作用域 | 弹窗、菜单、提示层经 Portal／Teleport 或独立窗口挂载后，主题变量、凹槽底色和无边框规则是否仍生效；不能仅凭源代码中的父子关系推断样式继承。 |
| 尺寸与文字 | 圆角、控件高度、内外间距、字号、字重、色阶、图标和箭头对齐是否与同类界面一致；字段标题与占位提示是否遵循项目约定。 |
| 主题与交互状态 | 用项目真实主题机制检查适用主题，以及本次涉及的默认、悬停、聚焦、展开、选中、禁用、错误状态；不能只看静态默认态。去除样式不能一并破坏键盘操作、控件语义和必要的焦点辨识。 |
| 布局与浮层 | 在项目支持的代表性窗口尺寸下，长文案、多选、错误提示和内容展开是否导致截断、横向溢出或遮挡；检查浮层定位、层级和可点击性、滚动归属、编辑区高度及保存／取消操作是否可达。 |

## 验证方法

- 通过已授权的运行入口或隔离夹具，渲染真实组件与项目真实样式。不得用手写近似 HTML、简化 CSS 或测试专属的样式修补证明产品 UI 合格；夹具只替换数据与外部依赖，不补齐产品缺失的样式作用域或参数。
- 尺寸、颜色、描边和溢出用浏览器计算样式、边界及命中测试核对，视觉层次与交互通过实际渲染观察。边框宽度非零但颜色透明不等于存在可见描边；反之，没有 border 类也不能排除轮廓线。关键发现按需保存截图，不要求每次审查做全量截图或像素差。
- 实际打开菜单／弹窗并操作，检查最终挂载节点；涉及表单时触发相关的空值／非法值提交，检查是否出现不符合项目要求的原生反馈。内容足以触发问题，不用恒为空、极短文案或始终禁用的按钮回避验证路径。
- 修改共享控件、全局 CSS 或作用域时，选取受影响的既有页面及相关主题／状态复核；局部源码审查不扩大为未经请求的全站重构。
- 自动化检查应观察最终计算样式、几何或用户操作结果，能拒绝已知错误实现；仅断言引用了某组件、存在 flex 类、没有原生标签，不能证明视觉一致。复用仍覆盖当前实现的有效证据，不无故重跑整套检查。

## 结论与边界

每项风格缺陷说明项目依据、触发条件、实际与预期差异、证据和最小调整方向，按用户影响分级；不将个人审美当成缺陷，也不因功能可用而忽略明确的风格违约。

已确认不符合要求的 UI 仍是未通过项；功能测试、类型检查或构建通过不能抵消。缺少渲染或目标平台条件时，完成可做的源码核对，明确哪些结论仅为推断，将未测主题／状态／平台列为未覆盖，不虚称整体验收通过。保持原有只读或已授权修复边界，不因发现问题自动获得改造、启动应用或发布授权。
