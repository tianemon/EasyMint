# 按风险选择检查

本表用于挑选证据，不是每次都必须完成的清单。先围绕用户报告、变更范围和故障后果排序。

| 方向 | 要核对的问题 | 有价值的证据 |
|---|---|---|
| 关键流程 | 所有分支都能到达明确终态吗？用户看到的完成是否对应实际结果？ | 追踪成功、失败、中断及恢复的完整流程 |
| 状态与配置 | 谁拥有状态？缓存、内存、持久化和客户端怎样同步？变更何时生效？ | 重开、重连、并发编辑及生效时机测试 |
| 并发与归属 | 哪些操作互斥？重入、乱序、重复消息和旧结果如何处理？可信身份来自哪里？ | 控制事件顺序；验证过期响应和错误所有者不能改变当前状态 |
| 失败与重试 | 等待是否有合理预算或取消途径？重试是否安全？超时后旧操作还会写入吗？ | 故障注入与副作用检查，包含取消后的迟到结果 |
| 资源生命周期 | 监听器、连接、任务、计时器、锁和临时文件由谁释放？ | 重复进入/退出，异常收尾及适当时长的资源曲线 |
| 性能与响应 | 用户等待发生在哪一段？测量是否受冷暖缓存、设备或服务波动影响？ | 同环境基线、阶段耗时、尾部延迟、代表性负载 |
| 代码与依赖残留 | 引用少是否真的无消费者？删除会切断哪些入口或契约？ | 入口图、注册点、发布配置、消费者搜索和删除后验证 |
| 升级与数据 | 明确支持哪些升级来源？中断或冲突后数据如何保留？ | 旧版本数据夹具、事务/恢复测试和已发布的兼容政策 |

## 流程、状态与取消

同时观察执行状态与展示状态。尤其检查请求尚在准备、后台任务继续执行、资源正在关闭，以及用户关闭界面后工作仍存在的时段。

多个客户端或进程存在时，核对操作归属及写入协调。客户端提交的资源 ID 只是定位信息，不能替代服务端的所有权检查；服务端派生的身份与路径也不应被载荷同名字段覆盖。

超时仅让调用方返回，不会自动取消底层操作。检查取消信号是否传递，迟到结果是否仍有效，锁与订阅何时释放。重试可能产生收费、发送、写入或发布副作用时，按实际风险验证幂等性或恢复策略。

关闭或删除资源前，分别核对取消请求、执行停止、输出排空与最终写入的完成条件，按实际运行库契约确认仍可能访问该资源的执行者已经收尾。尤其覆盖异步准备尚未进入运行态、关闭期间的迟到回调及重复关闭。固定延时不能替代停止确认；确认失败或超时应保留受影响数据并报告未完成，不提前返回“已关闭”。

预算来自产品体验、工作量、依赖行为或测量结果。避免把某次修复中的秒数套到所有任务，也避免为解决卡住而直接把真实忙碌状态改成空闲。

## 故障验证

针对实际边界选少量高价值场景：依赖不可用、响应变慢、操作取消、授权变化、写入冲突或恢复中断。先在可控夹具中复现；需要生产验证时明确对象、影响和停止条件。

同时核对调用方、后台执行、持久化与用户反馈。错误能返回但蒙版仍在、界面已结束但后台继续写、失败重试产生重复操作，都说明收尾不完整。

## 死代码与兼容清理

静态“不可达”可能是 worker、插件、路由注册、反射、命令入口、生成输出或打包入口。公共导出可能由仓库外调用，测试专用接口可能用于观察真实运行逻辑。先确认用途，不以引用数量作删除许可。

确认功能已退役后核对其界面、协议/声明、处理器、存储逻辑、依赖、说明及测试。移除仅验证废弃算法本身的用例，保留对现行行为有价值的回归覆盖。

迁移退役需要最低支持版本、旧数据来源和恢复策略的证据。经历多次发版不能证明用户都运行过中间版本。旧秘密或可执行配置仍可能存在，保护与数据删除需要独立判断。

孤儿清理、迁移清扫等依赖枚举结果的操作，先区分成功的空集合、读取失败与部分结果。只有识别范围完整且归属明确，才据此判断数据不存在；枚举或元数据识别不完整时保留相关数据。扫描与删除之间可能发生新写入，需验证它们不会被旧快照误删，并让失败或跳过原因可定位。

身份识别优先使用系统或 SDK 的权威元数据，核对缓存键、导入记录和恢复结果是否一致。文件名、目录名、显示名称与物理布局仅在契约明确保证时用于推导身份；兼容验证应覆盖合法自定义标识、改名或迁移后的存储布局，避免把约定外的名称直接视为孤儿。

## 性能与长期运行

根据实际架构测量：进程启动到可操作、首次反馈、取消完成、大数据读取、渲染/事件循环延迟、任务队列积压等。固定输入、环境和测量边界，报告样本范围；优先比较同环境下的回归，谨慎设定绝对阈值。

持续观察资源随循环次数或运行时间的变化，结合垃圾回收、连接池、缓存和后台工作解释曲线。一次增长不等于泄漏，一次下降也不能证明没有泄漏。需要更长观察才能判断时说明这一点。

先定位瓶颈再优化。避免仅为消除体积提示、追求零依赖或改善数字而删除有效能力；不能把缩短日志、隐藏错误或跳过验证计为性能收益。
