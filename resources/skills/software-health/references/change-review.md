# 变更审查与修复复核

用于指定提交、差异、未发布改动或修复复核。先确认用户要只读结论还是已授权修复，不把发现问题自动扩展为重构、提交或发布。

## 选择可靠的范围

以用户指定的提交、路径或改动为准。未指定时结合会话识别实际目标；若采用“未推送提交”，项目已有发布远端/分支约定时优先遵循并核实，可显式使用该引用；没有约定时再从当前分支与远端/跟踪关系识别基线。记录实际比较的基线与终点，不把某项目的约定推广到其他项目，也不把陈旧的本地远端引用当作已确认的远端最新状态。

检查工作树、暂存区和未跟踪文件，区分提交内容与其他在制改动。范围存在影响结论的歧义时澄清；可以独立审查的部分继续，不默认全仓扫描。不为审查默认切换分支、同步远端、整理 stash 或重写历史。无 Git 的项目按指定源码和可得基线检查，不要求初始化仓库。

## 将声称对应到实现

把用户要求、验收条件及相关说明逐项对应到代码路径和可观察结果。核对实现、注释、文档和实际输出中的行为、数字、清单及生效时机；有意改变的产品行为要与修复缺陷区分。

“完整”“全部”“只会”“总是”等承诺需要核对实现的过滤、截断、回退和异常分支。只完成部分需求时明确列出差额，不用笼统的“基本完成”代替。

## 检查影响面

| 方向 | 关键问题 |
|---|---|
| 逻辑与状态 | 边界输入、重复调用、短路副作用、竞态、重入和错误分支是否符合约定？ |
| 安全与归属 | 输入是否能越过路径/权限/所有权边界，是否泄漏秘密或改变可信元数据？ |
| 缓存与数据 | 缓存键、失效、持久化格式及标识变化会怎样影响已有数据和其他主体？ |
| 资源与失败 | 正常、失败、取消和卸载路径是否释放资源，重试是否产生重复副作用？ |
| 列举型清单 | 新增/改名的实体是否遗漏注册、序列化、校验、保护、显示映射或模型工具说明？ |
| 范围与约定 | 是否夹带其他改动、遗漏调用方、重复已有机制或违反项目约定？ |

对清单类改动先列出受影响的实体，再追查谁按名称或前缀枚举它们。项目已有机械守卫时复用，并补充守卫覆盖不到的路径；不要求每个仓库都有相同的清单或命令。

异常处理按语义判断：预期取消、明确回退或可选资源缺失可以有意不报错；意外错误被吞掉、反馈与真实结果矛盾、无法恢复才是需要指出的问题。不要仅按 `catch {}` 的形式定性。

第三方行为以项目实际依赖版本的契约、实现和必要实测为据，注释不能单独证明运行行为。需要归因到历史提交时核对相应提交及前后状态；跨多个提交的合并 diff 只能说明净变化，不能证明引入者。

声称为纯改名、搬迁或等价重构时，用同一输入、环境和测量方式核对代表性的输出与副作用；有功能变化就如实说明，不能藏在“只改名字”的描述里。

## 验证修复和断言是否有效

针对重要且可自动化的修复，验证：已知错误实现使目标断言失败，正确实现使它通过。失败必须来自目标行为，不能来自语法错误、环境缺失或不相关异常。不能安全还原旧缺陷时说明证据限制。

在隔离副本或合适的临时工作区中做反向探针，包含验证需要的未提交/未跟踪文件。不要在用户正在编辑的文件里先改坏、再用整文件还原；保存补丁也不代表包含了未跟踪内容。

检查夹具是否真的区分两个实现：不同优先级候选、顺序、相互遮蔽的值或边界条件必须能走到目标分支。仅有一个候选、多个分支返回相同值、宽泛文案命中通用回退，都可能让测试恒绿。

负向断言还要核对观察层：如果被禁止的产物根本不会进入被检查的输出，`not contains` 不能验证目标分支。在已知错误场景中，可先用正向包含探针确认产物确实可观察：**正向通过表示存在；正向失败表示未观察到**。随后用能拒绝错误实现的最终断言验证修复，不能只把断言取反就认为补强了测试。

依赖环境能力的负向用例先证明正常路径在该环境可运行，并核对预期的失败类型；任意非零退出码不等于权限边界生效。平台相关行为采用相应平台的输入、环境或集成测试，不为让测试变绿而把真实差异抹平。

UI 几何、尺寸和可访问性等可量化结论用实际计算值；视觉与交互判断结合实际渲染。没有渲染条件时标注推断，既不凭缩略图断言精确尺寸，也不要求所有审查都做截图或像素差。

环境提供 `web-ui-metrics-verify` 且任务涉及 Web UI 量测时，优先复用；没有该技能时使用项目已有的渲染/浏览器验证工具，不把专用技能设成硬依赖。

## 保留变更归属

只读审查不改动源代码、暂存区或历史。已授权修复时先检查目标处的真实改动，再应用最小修改；同文件有其他改动不必一律停工，但不能覆盖、移动或一起提交不属于本次工作的内容。确认存在不可安全分离的并发冲突时再协调。

已知存在并发写入者时，改动前核对当前分支、`git worktree list`、`git stash list`、工作树/暂存差异及目标文件的当前内容。最近提交与文件修改时间仅用于找线索，不能单独证明仍有活跃写入者。按实际文件和 hunk 判断交集；编辑前重读、提交前复查，发现同一处内容在变动或归属不清时先协调，不直接覆盖或搬走。没有并发迹象时不强制执行整套排查。

有提交授权时核对暂存的实际差异和依赖文件；按文件暂存仍可能带入同文件的其他 hunk。拆分提交以各提交自洽为前提，验证没有丢失原有改动。stash、恢复文件和重写提交属于独立操作，不作为例行审查步骤。

多仓库或多个工作区分别确认范围和归属，不能因另一个仓库也需要提交就把其中其他在制文件一并纳入。

## 输出可行动的结论

给出实际审查范围和验证环境。每条问题说明触发条件、预期与实际差异、位置/输出证据、影响和建议；区分已复现、源码可确定及未验证。

沿用项目严重度标准；没有标准时采用以下锚点，并说明影响及触发条件：

| 等级 | 默认判据 |
|---|---|
| P0 | 已确认的严重安全边界突破、不可恢复的数据破坏，或核心流程大范围不可用，需要阻断交付 |
| P1 | 已确认的重要功能或契约错误，或特定条件下的关键边界、恢复、兼容路径失效，应优先修复 |
| P2 | 影响有限的缺陷，或有具体后果的可维护性/一致性问题，可计划修复 |

偏好和无证据的未来风险与缺陷分开，不将所有错误结果都列为最高级。

有问题时优先列出有证据、可行动的问题，再说明检查结果和限制；没有发现时列明覆盖与未覆盖。只读审查不写“已修复”，修复复核不能仅靠测试数量或重新阅读 diff 宣称守护有效。
