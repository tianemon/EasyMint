# 模块与数据链路审查

用于页面、模块或子系统的现有实现，范围不局限于某批 diff。先明确模块入口、职责和对外契约，只沿实际相关的上下游扩展。

## 入口与可达性

结合静态引用、导入/导出关系、配置、路由、事件注册、打包清单和外部消费者判断可达性。符号全文计数与“模块外没有调用”只用于筛选候选，不能直接证明死代码。

默认导出可能以另一个名称导入，动态入口可能没有直接符号引用；同名符号、注释和字符串也会干扰计数。检查真实的符号与模块关系，再核对运行时入口。出现一次可能是假阳性，出现多次也可能只是其他同名内容。

可执行的排查顺序：

1. 确认 lint/编译器未使用规则是否实际启用、属于 error 还是 warn、忽略哪些名称，以及警告是否影响退出码；读取相关输出，不只看 exit code。将结果用于局部变量、参数及导入排查。规则未启用、没有有效信号或目标是公开导出时，继续第 2—3 步，不在这里等待“全部未使用项”的结论。TypeScript 的 `noUnusedLocals`/`noUnusedParameters` 同样不负责证明公开导出无人使用。
2. 枚举范围内的导出，对符号做词边界全仓检索并查看上下文，形成候选列表；不要仅统计模块外引用，也不要将计数当作结论。
3. 使用语言服务、AST 引用分析或人工沿 import/re-export 解析真实符号关系，确认别名、默认导出、类型引用和作用域；然后核对配置、注册、打包及仓库外消费者。
4. 只有未找到合法消费者、动态入口或保留契约且已有清理授权时才移除，并跑调用链相关验证；消费者范围不可确定时保留为未验证候选。

区分产品用途、有效的测试观察接口与只维护废弃算法的测试。未来“也许会用”不是现行用途的证据；公开接口是否能退役则取决于消费者和兼容约定。证据不足时报告候选，不擅自删除。

## 检查输出与警告

识别实际生效的类型、规范及构建配置和退出码策略。退出码成功不一定表示没有警告，检查完整相关输出；只有怀疑缓存掩盖变化时才做无缓存复核。

按源码缺陷、环境能力、其他在制改动及平台差异归因。说明依据和未确定之处，不能仅凭失败文件恰好有未提交改动，就把失败归给用户。避免为了“全绿”跳过真实失败或扩大无关修改。

## 声明、实现与消费契约

对暴露的 API、消息、协议或类型，核对声明、运行实现及调用方；按架构选择客户端、适配层、服务、worker 或远端，不假设必须有跨进程层。

检查缺失实现、遗漏声明、字段命名、可选性、异步返回、错误结果、单位与生效时机。类型写法不同不必然构成缺陷；有意的抽象类型仍需要消费者在使用前正确收窄。

多个主体参与时，再核对身份、资源所有权、版本和能力协商；不能只看形状相同就断言语义一致。

## 从数据生产走到用户结果

选择承载功能或用户指引的关键字段，追踪：

`生产 → 转换/传输 → 存储或状态 → 消费 → 用户结果或后台副作用`

逐边检查含义、单位、默认值、丢弃条件和失败分支。特别看仅在异常、空值、重启或权限变化时走到的分支。

生产与消费不要求数量相等，也不要求所有字段都展示在界面上。判断的是承诺的行为是否有消费者：是否只传递却没有执行/呈现，是否被通用默认值遮蔽，用户是否因此无法完成操作或恢复。

同样反查消费端所期待的数据是否真的产生；检查反馈是否准确区分处理中、成功、失败、中止和部分完成。

## 核对附属清单与旧数据

模块中的角色、状态、字段或资源变化可能影响序列化、校验、权限清单、映射、缓存、文档和工具声明。追踪相关清单，不凭本模块可编译或测试通过认定影响面完整。

对已有记录、标识、指纹和审批结果，核对升级后的解释与恢复方式。依兼容政策判断重确认、失效或迁移是否合理，不把任何失配都判为缺陷，也不能让有意变化悄无声息。

## 验证与交付

优先用实际入口或契约边界验证代表性的完整路径；按风险加入失败、重复、并发和恢复场景。涉及修复复核或断言强度时，按需参考 [change-review.md](change-review.md) 的“验证修复和断言是否有效”。

报告已证实的问题、验证过的行为与未覆盖范围。模块只有局部证据时，不外推为全程序健康；已授权修复与仅提出建议明确分开。
