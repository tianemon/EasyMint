# AI 指令与工具契约

仅用于包含模型、Agent、提示词或模型工具调用的项目。目标是核对产品希望的行为、模型实际收到的上下文和运行时能力，而非扩写一份通用提示词。

## 审查实际组装结果

沿组装路径核对基础/自定义提示词、角色模板、项目规则、技能、历史经验、工具定义及动态系统反馈。单个字符串文件正确，不代表最终请求正确。

重点检查：

- 默认或自定义内容缺失时，是否按产品约定回落；不能静默丢失身份、能力或必要边界。
- 动态段与实际安装的工具、当前配置及生效时机一致；不存在的能力有替代方式或明确限制。
- 不重复注入同一规则、历史内容或结果。顺序有意设计，但不把“放在最后”当成权限或可信度机制。
- 内置模板更新确实到达已安装用户；自定义内容是否应保留，按产品既有编辑与升级约定决定。

## 核对语义契约

| 契约 | 检查方法 |
|---|---|
| 授权与执行权限 | 区分用户让做什么、系统允许什么；工具可调用不等于业务已授权 |
| 指令与资料 | 明确可信指令来源；文件、网页、工具输出及历史经验不能自行获得更高权限 |
| 角色与调度 | 模板宣称的模型、配置、分工、交接和状态管理应与执行器一致 |
| 工具发现 | 名称、参数、发现方式及可用条件遵循实际注册结果，不猜测可调用名称 |
| 项目适配 | 构建、测试、版本控制和文档动作应依赖真实项目能力；可选信息不应被模板强制要求 |
| 自主与澄清 | 目标清晰且已授权时推进；缺失信息确实影响结果或存在未授权取舍时才澄清 |
| 完成与失败 | 完成标准与验证证据相称；失败或中断有收尾与停止条件，避免无效循环 |

保留用户明确选择的产品语义。发现冲突时追查其来源和优先级，优先修正最小责任点，不靠反复追加“必须”“禁止”压过旧规则，也不为某次案例增加永久特例。

## 分层验证

确定性检查适合组装、开关、生效时机、工具清单、参数与取消传递。模型评测适合观察授权理解、角色决策、工具选择和失败应对。以架构与风险决定是否两者都需要。

选择代表性场景而非照抄历史案例。覆盖产品的关键分岔即可，例如信息是否充分、能力是否可用、依赖是否失败、上下文来源是否可信；断言应关注可观察行为，不固定回答措辞。

真实模型评测要记录模型/配置、输入版本、调用和停止预算、结果及用量。重要行为可用重复或变体场景观察稳定性；未完成或超时样本保留，不只挑成功结果。评测使用受控数据，不让模型建议直接成为真实副作用。

单回合“下一步怎么做”只能证明该场景下的决策表现，不能替代多轮工具执行、任务完成和用户体验验证。判断是否需要多轮评测时考虑被改变的契约和故障后果。

## 输入成本与响应

分别观察提示词、工具定义、技能目录、历史及结果的体量，以及首个反馈、总耗时和缓存情况。先做控制变量评测，再按场景选择是否拆分或按需注入；避免仅为缩短文本而破坏关键行为。

模型中止后服务端可能继续处理或计费；没有返回用量不代表成本为零。使用隔离或测试账户时仍要核对令牌刷新、外部状态和费用是否得到授权，避免在临时凭据副本上刷新后使真实会话失效。
